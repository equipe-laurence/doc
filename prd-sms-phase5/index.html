Mini PRD — Phase 5 : Finalisation SMS Azure Communication Services¶

Projet : EquipeLaurence — Azure Function App
Phase : 5 — Azure Communication Services SMS Completion
Date : 2026-05-13
Demandeur : Eric Decarufel
Statut : Brouillon

1. Objectif¶

Les phases précédentes (BL-011, BL-012, BL-013) ont livré l'envoi de SMS d'urgence, la gestion des désabonnements (opt-out) et la piste d'audit. Cependant, l'audit actuel ne confirme que l'acceptation de l'envoi par Azure Communication Services — pas la livraison réelle sur le téléphone du destinataire.

Cette phase complète la boucle en :

  • capturant le statut de livraison final (delivered / failed / undelivered) via les callbacks asynchrones de Azure Communication Services ;
  • exposant un historique des diffusions passées et leurs statuts de livraison par une API REST ;
  • fournissant un guide d'intégration pour les appelants externes.

2. Portée¶

In scope ✅¶

  • Azure Function HTTP trigger pour recevoir les callbacks de statut Azure Communication Services (POST /api/sms/status-callback)
  • Table Azure Storage SmsDeliveryStatus pour persister le statut par MessageId
  • Mise à jour du résumé de diffusion (SmsAuditEntry) : compteurs delivered, failed, undelivered
  • Endpoint GET /api/sms/broadcasts — liste paginée des diffusions passées
  • Endpoint GET /api/sms/broadcasts/{idempotencyKey} — détail d'une diffusion (résumé + statuts par destinataire)
  • Guide d'intégration API (fichier Markdown + collection Bruno mise à jour)
  • Tests unitaires et BDD pour les nouveaux composants

Out of scope ❌¶

  • Interface web / dashboard
  • Notifications push / alertes en temps réel (SignalR, webhooks sortants)
  • Réenvoi automatique des messages échoués
  • Export PDF ou Excel des rapports
  • Rôles Azure AD supplémentaires (l'auth AAD existante est suffisante)
  • Support de fournisseurs SMS autres que Azure Communication Services

3. Exigences fonctionnelles¶

3.1 Callback de statut Azure Communication Services¶

FR-01 — Le système DOIT exposer un endpoint POST /api/sms/status-callback accessible sans authentification AAD (Azure Communication Services ne supporte pas OAuth), mais validé par signature HMAC-SHA1 Azure Communication Services.

FR-02 — À la réception d'un callback, le système DOIT persister dans SmsDeliveryStatus : MessageId, To (numéro masqué), MessageStatus, ErrorCode (si présent), TimestampUtc, IdempotencyKey (clé de corrélation).

FR-03 — Le système DOIT mettre à jour les compteurs DeliveredCount, FailedCount, UndeliveredCount dans l'entrée SmsAuditEntry correspondante, de façon idempotente (un même callback reçu deux fois ne doit pas incrémenter deux fois).

FR-04 — Les callbacks dont la signature Azure Communication Services est invalide DOIVENT retourner HTTP 403 sans traitement.

FR-05 — Le système DOIT ignorer silencieusement (HTTP 204) les statuts intermédiaires non pertinents (queued, sending, sent) afin de ne stocker que les états finaux : delivered, failed, undelivered.

3.2 API Historique des diffusions¶

FR-06 — GET /api/sms/broadcasts DOIT retourner une liste paginée (page + pageSize, défaut 20, max 100) des diffusions, triée par TimestampUtc décroissant, incluant : IdempotencyKey, TimestampUtc, LocationCode, RequesterPrincipal, RecipientCount, DeliveredCount, FailedCount, UndeliveredCount, PendingCount.

FR-07 — GET /api/sms/broadcasts/{idempotencyKey} DOIT retourner le détail d'une diffusion : le résumé de l'audit + la liste des statuts par destinataire (numéro masqué, statut, code d'erreur si applicable).

FR-08 — Les deux endpoints DOIVENT exiger une authentification AAD (Bearer token) identique à POST /api/sms/send.

FR-09 — Si {idempotencyKey} n'existe pas, le système DOIT retourner HTTP 404 avec un message d'erreur structuré.

FR-10 — PendingCount DOIT refléter RecipientCount - DeliveredCount - FailedCount - UndeliveredCount pour indiquer les messages dont le statut final n'est pas encore reçu.

3.3 Documentation¶

FR-11 — Un fichier docs/guide-sms-integration.md DOIT documenter : authentification, tous les endpoints (request/response exemples), gestion des erreurs, politique d'idempotence et la procédure de test avec Bruno.

FR-12 — La collection Bruno DOIT être mise à jour avec des requêtes pour les deux nouveaux endpoints GET.

4. Exigences non-fonctionnelles¶

NFR-01 — Performance : Le callback de statut DOIT traiter et répondre en moins de 500 ms (p95). Azure Communication Services abandonne les callbacks lents et retente — un traitement lent risque des doublons.

NFR-02 — Idempotence : Chaque callback Azure Communication Services peut être livré plusieurs fois. Toute écriture dans SmsDeliveryStatus et tout incrément de compteur DOIVENT être idempotents (upsert basé sur MessageId + MessageStatus).

NFR-03 — Sécurité — Validation HMAC : La signature Azure Communication Services (X-Azure Communication Services-Signature) DOIT être vérifiée sur chaque callback entrant. Le secret de validation (ACS_AUTH_TOKEN) DOIT être stocké dans Azure Key Vault, jamais en clair dans la configuration.

NFR-04 — Sécurité — Masquage des numéros : Les numéros de téléphone stockés et exposés via l'API DOIVENT être masqués (+1416****678). Le numéro complet n'est jamais retourné par l'API d'historique.

NFR-05 — Conformité : La rétention des entrées SmsDeliveryStatus DOIT respecter la politique de rétention configurée sur le compte de stockage (alignée avec SmsAuditEntry).

NFR-06 — Observabilité : Chaque callback reçu DOIT générer un log structuré avec MessageId, MessageStatus, IdempotencyKey. Les callbacks rejetés (signature invalide) DOIVENT être loggés en LogWarning.

NFR-07 — Tolérance aux pannes : Si la persistance du statut échoue (ex. : Table Storage indisponible), le système DOIT retourner HTTP 500 pour que Azure Communication Services retente. Ne pas avaler l'exception silencieusement.

5. Approche architecturale¶

5.1 Composant A — Azure Communication Services Status Callback Function¶

POST /api/sms/status-callback
  → Valider signature HMAC-SHA1 (IAzure Communication ServicesSignatureValidator)
  → Parser le payload form-urlencoded Azure Communication Services
  → Filtrer les statuts non-finaux → HTTP 204
  → ISmsDeliveryStatusRepository.UpsertAsync()   → SmsDeliveryStatus table
  → ISmsAuditRepository.IncrementDeliveryCountersAsync()  → SmsAuditEntry table
  → HTTP 204
  • Nouvelle interface : IAzure Communication ServicesSignatureValidator dans Core/Clients/
  • Nouvelle interface : ISmsDeliveryStatusRepository dans Core/Repositories/
  • Implémentation : Azure Communication ServicesSignatureValidator + TableStorageSmsDeliveryStatusRepository dans Infrastructure

5.2 Composant B — Table de statut de livraison¶

Table Azure Storage : SmsDeliveryStatus

Propriété Type Description
PartitionKey string IdempotencyKey
RowKey string MessageId
MaskedTo string Numéro masqué
MessageStatus string delivered / failed / undelivered
ErrorCode string? Code d'erreur Azure Communication Services si applicable
TimestampUtc DateTimeOffset Horodatage du callback

Modèle : SmsDeliveryStatusEntry dans Core/Models/

5.3 Composant C — API Historique des diffusions¶

GET /api/sms/broadcasts
  → Vérifier token AAD
  → INethrisReportSyncService... (non applicable)
  → ISmsAuditRepository.ListAsync(page, pageSize)  → SmsAuditEntry table
  → Projeter vers BroadcastSummaryDto[]
  → HTTP 200

GET /api/sms/broadcasts/{idempotencyKey}
  → Vérifier token AAD
  → ISmsAuditRepository.GetAsync(idempotencyKey)   → SmsAuditEntry table
  → ISmsDeliveryStatusRepository.ListByBroadcastAsync(idempotencyKey)
  → Assembler BroadcastDetailDto
  → HTTP 200 | 404

Nouveaux DTOs dans Core/Models/ :

  • BroadcastSummaryDto — résumé pour la liste
  • BroadcastDetailDto — détail avec IReadOnlyList<RecipientStatusDto>
  • RecipientStatusDto — numéro masqué, statut, code d'erreur

6. Critères d'acceptation¶

AC-01 — Après un envoi SMS, dans un délai raisonnable, GET /api/sms/broadcasts/{key} retourne des compteurs DeliveredCount ou FailedCount supérieurs à 0 (validé via Azure Communication Services test credentials).

AC-02 — Un callback avec une signature HMAC invalide reçoit HTTP 403 et ne modifie aucune donnée.

AC-03 — Un même callback Azure Communication Services envoyé deux fois n'incrémente les compteurs qu'une seule fois.

AC-04 — GET /api/sms/broadcasts sans token AAD retourne HTTP 401.

AC-05 — GET /api/sms/broadcasts/{keyInexistant} retourne HTTP 404.

AC-06 — GET /api/sms/broadcasts?page=1&pageSize=5 retourne au plus 5 résultats et inclut des métadonnées de pagination (totalCount, hasNextPage).

AC-07 — Les numéros de téléphone dans toutes les réponses API sont masqués.

AC-08 — La collection Bruno inclut des requêtes fonctionnelles pour les deux nouveaux endpoints GET.

AC-09 — La couverture de tests unitaires pour les nouveaux services atteint ≥ 80%.

AC-10 — docs/guide-sms-integration.md est suffisamment complet pour qu'un développeur externe puisse intégrer l'API sans aide supplémentaire.

Note budgétaire : Sur un total projet de 125 h, cette phase représente environ 30 % du budget restant après les phases précédentes. Le scope est volontairement limité à l'API — aucune interface web — pour rester dans l'enveloppe.

8. Dépendances et risques¶

Risque Mitigation
Azure Communication Services ne peut pas appeler un endpoint AAD protégé Le callback est validé par HMAC-SHA1, non par AAD — prévu dans FR-01
Délai de livraison des callbacks Azure Communication Services (minutes à heures) PendingCount gère l'état intermédiaire — prévu dans FR-10
Table Storage SmsAuditEntry non conçue pour les compteurs atomiques Utiliser TableClient merge optimiste avec ETag — documenter le pattern dans l'implémentation
Azure Communication Services retente les callbacks si HTTP != 2xx NFR-07 garantit HTTP 500 en cas d'erreur de persistance
