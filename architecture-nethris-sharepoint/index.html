Architecture d'intégration Nethris → SharePoint + SMS d'urgence¶

Vue d'ensemble¶

Ce document décrit l'architecture de l'application Azure Function qui :

  1. Synchronise les rapports Nethris — récupère les rapports automatisés du système RH Nethris et les téléverse dans une bibliothèque de documents SharePoint privée selon la planification Nethris:SyncSchedule (NCRONTAB — toutes les minutes par défaut, valeur provisionnée par Bicep). Un registre de synchronisation (Azure Table Storage) empêche les doublons.
  2. Envoie des SMS d'urgence — diffuse des messages textes (fournisseur Twilio ; Azure Communication Services conservé pour un éventuel retour arrière) aux employés d'un emplacement donné, avec gestion des opt-out, idempotence, et piste d'audit.

Diagramme des composantes Azure¶

Séquence du cycle de synchronisation¶

1. Fonction déclenchée (timer ou HTTP GET)
2. L'orchestrateur appelle INethrisAuthClient.LoginAsync() → identifiant de session
3. L'orchestrateur appelle INethrisReportClient.GetAvailableReportsAsync(sessionId)
4. Pour chaque rapport (trié par date d'exécution) — isolation d'erreur par rapport :
   a. ISyncLedger.TryClaimAsync(reportProdId) → passer si false (déjà réclamé)
   b. INethrisReportClient.DownloadReportAsync(sessionId, reportProdId) → contenu du rapport
   c. ISharePointClient.UploadFileAsync(rootFolder, baseFileName, bytes, contentType) → copie racine
   d. ISharePointClient.UploadFileAsync(archiveFolder, archiveFileName, bytes, contentType) → copie archive
   e. ISyncLedger.RecordSyncAsync(reportProdId, archivePath, syncedAtUtc, reportExecDate)
   f. (Optionnel) Si rapport source SMS : ingestion de l'index des destinataires
5. (Optionnel) Si IBaseTiIngestionService configuré : ingestion du classeur BaseTI
6. L'orchestrateur appelle LogoutSafelyAsync(sessionId, CancellationToken.None) dans le bloc finally
7. Retourne SyncCycleResult avec les résultats par rapport

Responsabilités par couche¶

Core (EquipeLaurence.Core)¶

Tout ce qui ne communique pas avec le monde extérieur.

  • Clients/ — Contrats pour les dépendances externes INethrisAuthClient, INethrisReportClient, INethrisRetryPolicy, ISharePointClient, ISyncLedger, ISmsClient, IRecipientIndexClient, IOptOutRegistryClient, ISmsAuditClient, ISmsIdempotencyStore, ISmsRecipientSource, IDeliveryStatusStore, IBaseTiRepository, IEmployeeExcelReader
  • Models/ — DTO — pas de logique, pas de dépendances NethrisReportSummary, NethrisReportContent, NethrisApiModels, SyncResult, SmsSendResult, RecipientRecord, SharePointFileInfo, BaseTiRecord, BaseTiIngestionResult, BroadcastSummary, BroadcastDetail
  • Configuration/ — POCO d'options (pattern Options) NethrisOptions, NethrisRetryOptions, SharePointOptions, LedgerOptions, BaseTiOptions, SmsOptions, AadAuthOptions (AcsOptions et TwilioOptions résident dans les projets EquipeLaurence.Infrastructure.Acs et EquipeLaurence.Infrastructure.Twilio)
  • Services/ — Orchestrateur — logique métier pure INethrisReportSyncService, NethrisReportSyncService, IBaseTiIngestionService

Gestion des secrets¶

  • Azure Key Vault stocke les secrets (mot de passe Nethris, secret client Entra ID, et — selon le fournisseur SMS — jeton Twilio / chaîne de connexion ACS). Les autres identifiants Nethris (AppId, BusinessCode, UserCode) sont des valeurs simples dans App Configuration.
  • Le Function App référence Key Vault via une identité managée (rôle Key Vault Secrets User, aucun mot de passe dans la configuration).
  • Azure App Configuration centralise les paramètres métier avec des références Key Vault intégrées ; seules les valeurs d'amorçage (AppConfiguration__Endpoint, Nethris__SyncSchedule, etc.) sont des app settings directs.
  • Les secrets Nethris et Entra ID (nethrisUserPasswordValue, azureAdClientSecretValue) sont transmis par .github/workflows/infra-deploy.yml à partir des secrets d'environnement GitHub (NETHRIS_USER_PASSWORD, AZURE_CLIENT_SECRET) plutôt que des fichiers de paramètres versionnés ; les valeurs Twilio (twilioAccountSidValue, twilioAuthTokenValue) ne sont pas transmises par ce workflow.

Stratégie de gestion des erreurs¶

Isolation par rapport¶

Chaque rapport se synchronise indépendamment. Une erreur sur un rapport n'interrompt pas le cycle — les autres rapports continuent d'être traités. Le SyncCycleResult rapporte tous les résultats, y compris les échecs.

Garantie de session Nethris¶

Le bloc finally de l'orchestrateur garantit que LogoutAsync est toujours appelé, même en cas d'exception. Cela empêche les fuites de session avec l'API Nethris.

Politique de réessai¶

Composant Stratégie
HTTP Nethris Polly sur HttpClient : exponentiel (3×, 2s/4s/8s) sur erreurs HTTP transitoires/408
API Nethris NethrisRetryPolicy (erreurs applicatives ReturnCode) : Nethris:Retry — 3 tentatives, délai initial 10 s, ×2
SharePoint Aucune politique Polly applicative dans SharePointClient
Registre sync Pas de réessai
Function Réessai auto du runtime

Journalisation et observabilité¶

  • Journalisation structurée via ILogger<T> partout.
  • Intégration Application Insights pour la télémétrie, les traces et les alertes.
  • Chaque cycle de sync journalise : heure de début, nombre de rapports, résultat par rapport, heure de fin.
  • Les échecs incluent les détails de l'exception pour le diagnostic.

Alertes¶

  • Configurer des alertes Application Insights pour :
  • Tout cycle de sync avec HasFailures == true
  • Échec complet du cycle de sync (exception non gérée)
  • Aucune activité de sync depuis 48 heures (vérification de la planification)

Système Authentification

Sécurité réseau¶

  • L'API Nethris requiert TLS 1.2 avec des suites de chiffrement spécifiques.
  • Tous les appels sortants passent exclusivement par HTTPS.
  • Le Function App peut optionnellement utiliser l'intégration VNet pour contrôler le trafic sortant.
  • Aucune exposition réseau entrante au-delà du runtime Functions.

Principe du moindre privilège¶

  • Utilisateur de service Nethris : accès en lecture seule (getList, getFile uniquement).
  • Inscription d'application SharePoint : permission Sites.Selected limitée au site cible uniquement.
  • Table Storage : rôle Storage Table Data Contributor attribué à l'identité managée du Function App au niveau du compte de stockage (infra/main.bicep).

Structure de dossiers SharePoint¶

Chaque rapport est téléversé en deux copies : une copie « racine » à la racine du RootFolder configuré (/FSources/Nethris en production), dont le nom est stable (remplacée à chaque nouvelle exécution), et une copie d'archive horodatée dans le sous-dossier ARCHIVES/. Il n'y a pas de sous-dossiers par année, mois ou jour.

Bibliothèque de documents SharePoint
└── FSources/
    └── Nethris/
        ├── Emp2.xlsx
        ├── Nom00.xlsx
        └── ARCHIVES/
            ├── Emp2_20260501_010140.xlsx
            └── Nom00_20260501_010140.xlsx

Format du nom de fichier : copie racine {NomRapport}.{ext} ; copie d'archive {NomRapport}_{yyyyMMdd_HHmmss}.{ext}.

Les noms sont construits dans NethrisReportSyncService.BuildBaseFileName() et BuildArchiveFileName() (via SanitizeReportName) : les caractères hors [\w\-. ] sont remplacés par _, le nom est tronqué à 200 caractères, l'extension est limitée à pdf, csv, xlsx ou xls (sinon bin), et l'horodatage de l'archive provient de ExecutionDateUtc du rapport Nethris. Le chemin enregistré dans le registre est celui de la copie d'archive.

Pipeline SMS d'urgence¶

Le pipeline SMS permet de diffuser un message d'urgence à tous les employés éligibles d'un emplacement donné.

Flux d'envoi (POST /api/sms/send)¶

  1. Validation du jeton porteur Azure AD (Microsoft.Identity.Web).
  2. Extraction de l'en-tête Idempotency-Key — rejet si absent.
  3. Vérification de l'idempotence (ISmsIdempotencyStore) — rejeu de la réponse en cache si déjà traité.
  4. Lecture des destinataires pour l'emplacement (ISmsRecipientSource.GetByLocationAsync), résolus depuis la table BaseTi.
  5. Filtrage des opt-out (IOptOutRegistryClient.IsOptedOutAsync).
  6. Envoi individuel via ISmsClient.SendSmsAsync pour chaque destinataire éligible.
  7. Enregistrement de la piste d'audit (ISmsAuditClient.RecordBroadcastAsync) — le corps du message est stocké uniquement sous forme de hash SHA-256.
  8. Mise en cache de la réponse pour l'idempotence.

Webhooks entrants¶

  • POST /api/sms/inbound/twilio (TwilioInboundSmsFunction) : validation de la signature X-Twilio-Signature, extraction du mot-clé (STOP/ARRET/START/UNSTOP…) et mise à jour du registre opt-out/opt-in (IOptOutRegistryClient).
  • POST /api/sms/delivery-status (AcsDeliveryStatusFunction) : réception des événements Event Grid de statut de livraison (validation d'abonnement incluse).

Pour le détail des fonctionnalités SMS, voir la documentation SMS dédiée.

Activation conditionnelle¶

Le fournisseur SMS est déterminé par Sms:Provider (Twilio, Acs ou Disabled). Si la clé est absente, Acs est déduit quand Acs:ConnectionString et Acs:PhoneNumber sont présents, sinon Disabled. Seul Twilio enregistre un client d'envoi réel (TwilioSmsClient) ; Acs et Disabled injectent DisabledSmsClient (stub inerte qui retourne un échec). Côté Bicep, smsEnabled pilote Sms__Enabled et les settings AzureWebJobs.<Fonction>.Disabled.
