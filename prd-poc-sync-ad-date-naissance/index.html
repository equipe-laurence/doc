1. Contexte et objectif¶

1.1 Objectif final (hors portée de la POC)¶

Livrer un outil .NET qui s'exécute sur le serveur Active Directory (contrôleur de domaine, Q14), de façon planifiée par une expression cron lue dans une variable d'environnement (ADSYNC_SCHEDULE_CRON), et qui met à jour des attributs d'utilisateurs AD à partir de données publiées dans une table Azure Table Storage (le mode synchronisation), alimentée elle-même par le fichier Excel BaseTI (Q10). Il permet aussi à un opérateur de modifier manuellement un attribut pour un utilisateur (mode manuel : paramètres ou TUI interactif). La forme finale est un processus de longue durée (service Windows hébergeant le planificateur interne) ; le mode run-once reste disponible pour le Planificateur de tâches, les tests et les reprises (3.13).

Les données changent très peu (Q7) : un balayage périodique (polling) suffit ; aucune file, aucun déclencheur côté producteur.

1.3 Pourquoi une POC¶

Réduire les risques techniques avant d'investir : (1) accès Azure Table en HTTPS sortant depuis le serveur AD (Q5), (2) écriture réelle dans AD de production avec des droits minimaux et un filet de sécurité (restauration), (3) choix de l'attribut AD (date de naissance) — différé (Q12), (4) résolution fiable de l'utilisateur à partir du code unique, (5) validation de la forme « processus planifié sur le serveur AD » (cron en variable d'environnement, service Windows), (6) chaîne d'alimentation Excel → table → AD de bout en bout.

2. Objectifs, non-objectifs, critères de succès, hypothèses¶

2.1 Objectifs de la POC¶

  • O1 — Lire dans la table Azure la valeur d'un attribut (date de naissance) pour un utilisateur identifié par son code unique.
  • O2 — Résoudre de façon non ambiguë (exactement 1 objet) l'utilisateur AD correspondant au code unique (préfixe du courriel).
  • O3 — Écrire un attribut de la liste blanche dans AD, avec un compte à privilèges minimaux, sans jamais journaliser la valeur (seule la console interactive du service peut afficher les valeurs des attributs Sensitive: false, voir G13).
  • O4 — Garantir l'idempotence (relancer ne produit ni effet de bord ni erreur) par comparaison avant/après lecture de la valeur AD.
  • O5 — Permettre le choix de l'attribut et de la valeur par paramètres de la console et par un TUI interactif ; le mode non interactif reste disponible.
  • O6 — Fournir un mode dry-run par défaut, une sauvegarde de l'ancienne valeur et une commande de restauration (rollback).
  • O7 — Valider une architecture réutilisable telle quelle dans la forme finale planifiée (section 6).
  • O8 — Exécuter la synchronisation selon une expression cron fournie par variable d'environnement (mode watch), sans chevauchement, avec arrêt propre (3.13).

2.2 Non-objectifs¶

  • Environnement de test AD, OU de test ou compte de test à créer (non disponible ; voir section 7 pour la stratégie de remplacement).
  • Plusieurs utilisateurs par exécution en mode --apply pendant la POC (au-delà de la limite configurée), parallélisme, volumétrie.
  • Création/désactivation de comptes, réinitialisation de mot de passe, écriture d'attributs hors liste blanche.
  • Extension du schéma AD.
  • File de messages / déclencheur côté producteur (Q7).
  • Évaluation des facteurs relatifs à la vie privée (ÉFVP) ou démarche formelle Loi 25 (Q6 : usage privé) — seule une hygiène légère est conservée (3.12).
  • Conception ou modification du producteur de la table.
  • Haute disponibilité / basculement entre contrôleurs de domaine.
  • Comparaison avec un budget ou une enveloppe (Q9) : les estimations sont informatives.

2.4 Hypothèses¶

  • H1 — Le serveur AD (contrôleur de domaine) de production qui héberge l'outil joint le DC local ou un autre DC (LDAP signé/chiffré) [Q3 : prod seulement ; Q14 : l'outil roule sur le serveur AD].
  • H2 — Accès sortant HTTPS du serveur AD vers *.table.core.windows.net (et login.microsoftonline.com si jeton Entra) autorisé ; aucun accès entrant (Q5). Un DC est souvent durci (sortie Internet restreinte) → règle explicite à obtenir (R9).
  • H3 — La table est la table BaseTI existante (réf. BaseTiTableStorageRepository), alimentée par l'ingestion du fichier Excel ; une ligne identifie l'utilisateur par la colonne « Code unique » (UniqueCode) ; la date de naissance sera une nouvelle colonne issue du même fichier (Q10/Q11, confirmé par le propriétaire) — non présente dans le code ni dans le classeur de référence aujourd'hui (3.6).
  • H4 — Le code unique est de la forme <première lettre du prénom><nom de famille> et correspond au préfixe du courriel (Q2). Observation (classeur de référence) : pour un prénom composé, le code semble utiliser les initiales (ex. JF…) et la casse est mélangée → règle à confirmer (Q15).
  • H5 — L'attribut AD de la date de naissance n'est pas encore choisi (Q12) ; pour la POC, il est fourni par paramètre et doit figurer dans la liste blanche configurée. Un attribut libre sera confirmé en lecture seule avant la 1ʳᵉ écriture.
  • H6 — Le projet vit dans ce dépôt (.NET 10, Directory.Build.props : Nullable, ImplicitUsings, TreatWarningsAsErrors).
  • H7 — Usage privé : pas de démarche Loi 25 formelle (Q6) ; les données réelles de production sont utilisées, d'où le renforcement de la sécurité opérationnelle.
  • H8 — Identité d'exécution (Q13, interprétation à confirmer — Q18) : l'outil s'exécute sous le compte Windows authentifié qui lance le processus ; authentification AD intégrée (Kerberos/Negotiate), aucun identifiant AD en configuration.
  • H9 — Fréquence (Q14) : fournie par une variable d'environnement contenant une expression cron ; le fuseau horaire est explicite (3.13).

Flux logique d'un sync (le mode manuel set saute les étapes 2–3) :

  1. Charger/valider la configuration (IOptions<T> + ValidateOnStart), vérifier le cadenas (ApplyEnabled, AllowedUsers, liste blanche).
  2. Lire dans la table les lignes visées (filtre sur AllowedUsers en POC) — lecture seule.
  3. Pour chaque ligne et chaque attribut mappé : normaliser/valider la valeur.
  4. Résoudre l'utilisateur AD par code unique (3.4) — exactement 1 objet, dans AllowedSearchBase.
  5. Lire la valeur AD courante ; si identique → AlreadyUpToDate.
  6. Sinon : en dry-run, rapporter ; en --apply, sauvegarder l'ancienne valeur (3.11), écrire, relire et vérifier.
  7. Journaliser (sans valeurs), produire le rapport, retourner le code de sortie.

Changement de conception (rév. 2). La table n'est plus un « journal de changements » avec statuts (Pending → Applied). C'est une source d'état : la valeur désirée de l'attribut pour chaque utilisateur. L'outil réconcilie (compare table ↔ AD) et n'écrit que dans AD. Raisons : (1) le principe de moindre privilège côté Azure (rôle lecteur, pas de CreateIfNotExists) ; (2) l'ingestion BaseTI existante exécute ReplaceAllAsync (suppression/remplacement des entités) — un statut écrit par l'outil dans ces lignes serait effacé à la prochaine ingestion ; (3) données qui changent peu → le balayage idempotent est plus simple et robuste qu'un protocole de réclamation par ETag ; (4) l'idempotence repose sur la valeur AD, pas sur un état tiers.

3.4 Identification de l'utilisateur AD (Q2)¶

Identifiant : code unique <première lettre du prénom><nom de famille> = préfixe du courriel (ex. jdoe pour jdoe@domaine).

Normalisation (identique des deux côtés) : Trim, minuscules invariantes, décomposition Unicode (FormD) et retrait des diacritiques (é→e, ç→c), ligatures (œ→oe), puis traitement des traits d'union, apostrophes et espaces selon une règle configurable CodeNormalization (valeur par défaut provisoire : les retirer ; règle définitive → Q15, non bloquant : le dry-run liste les écarts). Observation (classeur de référence) : le code d'un prénom composé semble formé des initiales de chaque composant (ex. JF + nom) avec une casse mixte ; la comparaison est donc insensible à la casse et le contrôle de cohérence (ci-dessous) compare le code aux initiales de tous les composants de givenName, pas seulement à la 1ʳᵉ lettre (Q15).

Stratégie de recherche (sous AllowedSearchBase, portée sous-arbre, valeurs exactes, sans caractère générique, échappement RFC 4515).

Défaut depuis le 2026-10-20 : userPrincipalName seulement, car le UPN est l'adresse courriel de l'utilisateur (AdSync:MatchOn = UserPrincipalName). La table BaseTi ne publie pas de courriel : l'adresse est reconstruite à partir du code (<code>@<suffixe-UPN-autorisé>, AdSync:UpnSuffixes). Il y a une recherche par suffixe configuré.

(&(objectCategory=person)(objectClass=user)
  (userPrincipalName=<code>@<suffixe-UPN-autorisé>))

Les stratégies Mail (mail=<code>@<domaine-autorisé>, AdSync:MailDomains) et SamAccountName (sAMAccountName=<code>, codes de 20 caractères au plus) restent disponibles par configuration (ex. AdSync:MatchOn = "UserPrincipalName, Mail"). Chaque stratégie retenue est une recherche distincte ; les résultats sont fusionnés par objectGUID. Aucune stratégie exploitable (ex. UserPrincipalName sans UpnSuffixes) est une erreur de configuration : le cycle s'arrête plutôt que de conclure « introuvable » pour tous.

Règle Détail

3.5 Attributs AD et liste blanche (Q1)¶

L'outil est générique mais fermé par défaut : seul un attribut déclaré dans AdSync:AllowedAttributes peut être lu, comparé ou écrit. Liste d'interdits intégrée (G16, non contournable). 3.11 Journalisation, audit, sauvegarde et restauration¶

  • ILogger (console + fichier) ; événements structurés : RunId, CorrelationId, UserCode, DN, nom de l'attribut, statut/raison, mode (dry-run/apply/manual), durée. Jamais la valeur ancienne/nouvelle ; au plus un indicateur « modifiée : oui/non » et la longueur. Jamais d'identifiants, jetons ni chaînes de connexion.
  • Rapport d'exécution (fichier) : une ligne par utilisateur — code, raison, Changed (booléen). Sans valeurs.
  • Sauvegarde pour restauration : avant écriture, l'ancienne valeur (ou « absente ») est écrite dans un fichier chiffré DPAPI (portée machine ou utilisateur), ACL restreinte au compte d'exécution, rétention configurable (p. ex. 30 jours, purge au démarrage). Ce fichier est le seul endroit où la valeur existe côté outil ; il est exclu du dépôt et des journaux.
  • rollback --run-id <id> relit la sauvegarde et restaure (dry-run par défaut ; --apply pour exécuter ; mêmes garde-fous).
  • Piste côté AD : événement 5136 (voir 3.8).

3.13 Planification et hébergement sur le serveur AD (Q7, Q14)¶

Réponse du propriétaire (Q14) : le code roule sur le serveur AD ; la fréquence est une expression cron dans une variable d'environnement. Conséquence de conception : le planificateur est interne à l'application (et non le Planificateur de tâches Windows), ce qui fait de l'outil, dans sa forme finale, un processus de longue durée / service Windows.

Option Avantages Inconvénients Décision
Planificateur interne (watch, Cronos) Respecte Q14 (cron en variable d'environnement) ; fuseau et chevauchement maîtrisés dans le code et testables ; même cœur que run-once Processus permanent (supervision, journalisation d'un service) ; le code de sortie par exécution disparaît → il faut un signal de santé (ci-dessous) Retenue
Planificateur de tâches Windows (run-once) Aucun processus permanent ; code de sortie natif ; gestion des droits de l'ordonnanceur La fréquence ne vient plus d'une variable d'environnement (définition de tâche) ; sur un DC, le droit « ouvrir une session en tant que tâche » doit être accordé par stratégie Conservée en secours (le mode sync run-once reste pleinement supporté, et sert aux tests/reprises)
Service Windows sans planificateur interne — Ne respecte pas Q14 Écartée

Bibliothèque : Cronos (analyse cron 5 champs, GetNextOccurrence avec TimeZoneInfo, gestion des changements d'heure ; MIT) plutôt que NCrontab (pas de gestion native du fuseau/DST). Une dépendance NuGet de plus (surface minimale, R12).

Variables d'environnement (proposition) :

Variable Rôle Défaut / validation
ADSYNC_SCHEDULE_CRON Expression cron 5 champs (ex. 30 6 * * * = chaque jour à 06 h 30) Obligatoire pour watch (sinon code 2) ; syntaxe invalide → refus de démarrer (code 2) ; priorité : --schedule > variable > configuration
ADSYNC_SCHEDULE_TZ Fuseau horaire d'interprétation du cron (identifiant IANA ou Windows) Défaut = fuseau local du serveur, journalisé au démarrage ; recommandé : le définir explicitement (un serveur AD est parfois en UTC)
ADSYNC_SCHEDULE_RUN_ON_START Exécute une fois au démarrage avant d'attendre la 1ʳᵉ occurrence false ; aucun rattrapage des occurrences manquées (si le service était arrêté, on attend la prochaine)
ADSYNC_SCHEDULE_MIN_INTERVAL_MIN Intervalle minimal accepté entre deux occurrences 15 min ; un cron plus fréquent (ex. * * * * *) → refus (code 2) sauf abaissement explicite (tests)
ADSYNC_ATTRIBUTE Nom de l'attribut cible de watch (équivalent de --attribute, Q12) Aucun ; doit figurer dans la liste blanche

Les variables ne contiennent aucun secret. Pour un service Windows, elles sont définies au niveau du service (ou de la machine) et ne sont lues qu'au démarrage : un changement de cadence exige un redémarrage du service (documenté au runbook).

Comportement de watch :

  • Fuseau et changements d'heure : les occurrences sont calculées par Cronos dans le fuseau configuré, converties en UTC pour l'attente ; au passage à l'heure d'été, une occurrence « sautée » est exécutée juste après la transition ; au retour à l'heure normale, une occurrence à heure fixe n'est exécutée qu'une fois. Éviter de planifier entre 02 h et 03 h ; le comportement de la combinaison jour du mois + jour de la semaine est vérifié par tests (ne pas restreindre les deux).
  • Boucle d'attente : recalcul de la prochaine occurrence à chaque réveil avec une attente plafonnée à 60 s (résiste aux dérives d'horloge, à la mise en veille et aux corrections d'heure) ; au démarrage, journalisation de l'expression, du fuseau et des 3 prochaines occurrences (UTC et locale).
  • Prévention des chevauchements : (1) mutex nommé Global\EquipeLaurence.AdSync (G12) — une 2ᵉ instance (autre service, tâche, TUI en écriture) se termine ; (2) dans le processus, un tick qui survient pendant une exécution est sauté (journalisé « exécution précédente en cours »), jamais empilé ; (3) délai maximal d'une exécution (ProcessingTimeout, défaut 10 min) au-delà duquel l'exécution est annulée entre deux utilisateurs.
  • Arrêt propre : Ctrl+C / SIGTERM / arrêt du service → CancellationToken ; l'exécution en cours termine l'utilisateur en cours (la séquence sauvegarde → écriture → relecture est une section critique non interrompue, bornée par ProcessingTimeout), n'en démarre pas d'autre, libère le mutex, journalise l'arrêt et rend le code 0 ; le délai d'arrêt de l'hôte est réglé en conséquence (HostOptions.ShutdownTimeout) et le service déclare un temps d'attente d'arrêt suffisant.
  • Dry-run par défaut : watch ne s'exécute en écriture que si --apply et ApplyEnabled=true et l'interrupteur G11 n'est pas actif ; il relit la configuration/l'interrupteur à chaque occurrence (l'arrêt d'urgence n'exige pas de redémarrage).
  • Signal de santé (remplace le code de sortie par exécution) : à la fin de chaque exécution, écriture d'un fichier d'état (last-run.json : horodatage, code, compteurs ; sans valeur) et d'une entrée du journal des événements Windows (Erreur si code ≠ 0) pour l'alerte ; l'alerte « aucune exécution réussie depuis N occurrences » est possible via ce fichier (destinataire de l'alerte : Q18).
  • Hôte : POC = application console watch au premier plan ; forme finale = service Windows (UseWindowsService(), Microsoft.Extensions.Hosting.WindowsServices) exécuté sous un gMSA, démarrage automatique différé, récupération sur échec. Le cœur (DirectorySyncService) reste indépendant de l'hôte ; WI-18 couvre le mode watch, le packaging en service relève de WI-13.
  • Aucune file (Q7) : la fréquence faible reste adaptée à un balayage périodique (p. ex. quotidien).

4. Exigences fonctionnelles de la POC¶

  • FR-01 — sync DOIT lire la table en lecture seule et réconcilier les attributs mappés pour les utilisateurs de AllowedUsers.
  • FR-02 — Le programme DOIT résoudre l'utilisateur par le code unique selon 3.4 et exiger exactement un objet, sous AllowedSearchBase.
  • FR-03 — Le programme DOIT écrire un attribut de la liste blanche seulement si la valeur diffère, si --apply est fourni et ApplyEnabled=true.
  • FR-04 — set DOIT permettre de choisir l'attribut et la valeur par paramètres (valeur sensible : stdin/variable d'environnement, jamais en clair sur la ligne de commande).
  • FR-05 — Le TUI DOIT permettre le même parcours (utilisateur → attribut de la liste → valeur masquée → dry-run → confirmation typée) et n'utiliser que les services partagés.
  • FR-06 — Le mode non interactif DOIT rester disponible et ne JAMAIS demander d'entrée.
  • FR-07 — Le programme DOIT sauvegarder l'ancienne valeur avant écriture et fournir rollback.
  • FR-08 — Le programme DOIT appliquer les limites G8–G9 et l'interrupteur G11.
  • FR-09 — Le programme DOIT retourner les codes de sortie de 3.10.
  • FR-10 — Le programme NE DOIT PAS journaliser de valeur d'attribut ni de secret.
  • FR-11 — Le programme NE DOIT PAS écrire dans la table Azure.
  • FR-12 — watch DOIT lire l'expression cron dans ADSYNC_SCHEDULE_CRON (ou --schedule), refuser de démarrer si elle est invalide, interpréter le cron dans le fuseau configuré, ne jamais exécuter deux synchronisations en parallèle (mutex G12 + saut de tick) et s'arrêter proprement (3.13).

  • FR-15 — Le programme DOIT lire BirthDate (chaîne yyyy-MM-dd) depuis la table et la valider strictement (3.6) ; une valeur absente ou invalide n'écrit rien.

  • Observabilité : journaux structurés, corrélation par RunId.
  • Portabilité : aucune logique métier dans Program.cs, Cli/ ou Tui/.
