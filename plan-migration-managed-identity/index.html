Plan de Migration — Managed Identity pour Graph API / SharePoint¶

Titre officiel: Plan de Migration vers Managed Identity — Élimination des Secrets Entra ID pour Graph API / SharePoint

Auteurs: Morpheus (Lead / Architect) + Dozer (Azure Engineer)
Date: 2026-06-18
Demandé par: Eric Decarufel
Statut: Approuvé — Prêt pour implémentation

Résumé exécutif¶

Actuellement, le Function App utilise ClientSecretCredential pour accéder à Microsoft Graph et SharePoint. Ce secret azure-ad-client-secret doit être roté manuellement, ce qui entraîne des pannes intermittentes et crée un risque opérationnel continu.

Solution : Remplacer ClientSecretCredential par DefaultAzureCredential avec le mode ManagedIdentity. Cette migration élimine le secret Entra ID du code applicatif en s'appuyant sur l'identité managée du Function App pour l'authentification auprès de Microsoft Graph.

Impact : - Une modification d'une seule ligne en C# (FunctionAppStartup.cs ligne 343) - Deux changements Bicep mineurs (modules appConfiguration et main) - Un script post-déploiement pour accorder la permission Sites.Selected à la MI - Le secret azure-ad-client-secret reste dans Key Vault pour Easy Auth (géré par la plateforme App Service) - Les développeurs locaux utiliseront az login — plus besoin de secrets dans local.settings.json

Risque: Très faible. Le secret Easy Auth reste, le secret Nethris reste, et le rollback est possible en 2 minutes sans redéploiement Bicep.

1. Inventaire des secrets et statut post-migration¶

Secret Utilisé par Peut être éliminé? Changement recommandé
nethris-user-password (KV) Nethris:UserPassword → NethrisReportClient ❌ Non Conserver dans Key Vault sans expiration forcée. Accès via MI uniquement. Aucun changement de code.
azure-ad-client-secret (KV) — Easy Auth MICROSOFT_PROVIDER_AUTHENTICATION_SECRET dans functionApp.bicep (résolu par la plateforme) ✅ Hors du code Conserver dans Key Vault pour Easy Auth. La plateforme gère la résolution. Aucun changement de code.
azure-ad-client-secret (KV) — Graph API / SharePoint AZURE_CLIENT_SECRET dans App Config → BuildGraphCredential → ClientSecretCredential ✅ ÉLIMINÉ Remplacer par GraphAuthMode.ManagedIdentity. Supprimer AZURE_CLIENT_SECRET, AZURE_TENANT_ID, AZURE_CLIENT_ID de App Config.
AZURE_CLIENT_SECRET dans local.settings.json IConfidentialClientApplication → AuthCallbackFunction (local uniquement) ✅ Optionnel Secret local uniquement, non committée, non expirable en prod. Documenter comme optionnel dans le template.

2. Insight architectural — Séparation des responsabilités¶

Le secret azure-ad-client-secret sert deux fins complètement différentes qui doivent être gérées indépendamment.

Usage A — Easy Auth (responsabilité de la plateforme)¶

MICROSOFT_PROVIDER_AUTHENTICATION_SECRET est une app setting du Function App configurée comme référence Key Vault dans functionApp.bicep :

// functionApp.bicep — ligne 139 (aucun changement requis)
{
  name: 'MICROSOFT_PROVIDER_AUTHENTICATION_SECRET'
  value: '@Microsoft.KeyVault(SecretUri=${keyVaultUri}secrets/${azureAdClientSecretSecretName}/)'
}

Ce secret est résolu par la plateforme App Service au démarrage. Il n'est jamais lu par le code C#. Aucun changement dans cette migration.

Usage B — Graph API (à éliminer)¶

AZURE_CLIENT_SECRET est actuellement lu par BuildGraphCredential dans FunctionAppStartup.cs quand SharePoint:AuthMode = ClientSecret (le défaut actuel). En activant ManagedIdentity, cette lecture ne se produit plus.

4. Changements de code C¶

FunctionAppStartup.cs — Ligne 343¶

Motivation: ManagedIdentityCredential() fonctionne uniquement sur Azure (IMDS). DefaultAzureCredential() fonctionne à la fois sur Azure (via MI) et localement (via az login). Ce changement élimine le besoin de AZURE_CLIENT_SECRET localement.

Avant : 

if (Enum.TryParse<GraphAuthMode>(authModeValue, ignoreCase: true, out var authMode)
    && authMode == GraphAuthMode.ManagedIdentity)
{
    return new ManagedIdentityCredential();
}

Après : 

if (Enum.TryParse<GraphAuthMode>(authModeValue, ignoreCase: true, out var authMode)
    && authMode == GraphAuthMode.ManagedIdentity)
{
    return new DefaultAzureCredential();
}

Justification : DefaultAzureCredential tente les sources dans cet ordre : 1. Environment variables 2. Workload Identity 3. Managed Identity (Azure IMDS) 4. Visual Studio 5. Azure CLI (az login) 6. Azure PowerShell 7. Interactive Browser

En production Azure, la MI répond en 1re position. En local avec az login, Azure CLI répond. Un seul credential, deux contextes.

Mise à jour du XML doc : Modifier le résumé de BuildGraphCredential pour refléter DefaultAzureCredential au lieu de ManagedIdentityCredential.

5. Changements Bicep¶

5.1 — infra/modules/appConfiguration.bicep¶

Supprimer — 3 ressources de configuration¶

// Supprimer ces 3 ressources :
resource configAzureTenantId 'Microsoft.AppConfiguration/configurationStores/keyValues@2024-05-01' = {
  parent: appConfig
  name: 'AZURE_TENANT_ID'
  properties: {
    value: azureAdTenantId
    contentType: 'text/plain'
  }
}

resource configAzureClientId 'Microsoft.AppConfiguration/configurationStores/keyValues@2024-05-01' = {
  parent: appConfig
  name: 'AZURE_CLIENT_ID'
  properties: {
    value: azureClientId
    contentType: 'text/plain'
  }
}

resource configAzureClientSecret 'Microsoft.AppConfiguration/configurationStores/keyValues@2024-05-01' = {
  parent: appConfig
  name: 'AZURE_CLIENT_SECRET'
  properties: {
    value: getAppConfigKeyVaultReference(getKeyVaultSecretUri(keyVaultUri, azureAdClientSecretSecretName))
    contentType: 'application/vnd.microsoft.appconfig.keyvaultref+json;charset=utf-8'
  }
}

Supprimer — 1 paramètre¶

// Supprimer ce paramètre (plus utilisé dans ce module après suppression de configAzureClientSecret)
param azureAdClientSecretSecretName string = 'azure-ad-client-secret'

Note importante : Les paramètres azureAdTenantId et azureClientId sont conservés dans le module car ils alimentent aussi les sections AzureAd:TenantId et AzureAd:ClientId (Easy Auth).

Ajouter — 1 ressource de configuration¶

// Activer Managed Identity pour Graph API / SharePoint
resource configSharePointAuthMode 'Microsoft.AppConfiguration/configurationStores/keyValues@2024-05-01' = {
  parent: appConfig
  name: 'SharePoint:AuthMode'
  properties: {
    value: 'ManagedIdentity'
    contentType: 'text/plain'
  }
}

6. Script post-déploiement — scripts/grant-sharepoint-mi-permissions.sh¶

La Managed Identity doit recevoir la permission Microsoft Graph Sites.Selected pour accéder à SharePoint.

⚠️ Cette étape ne peut pas être automatisée en Bicep — le standard Bicep ne supporte pas encore l'extension Microsoft Graph (elle est en preview). Créer un script versionné dans le repo et l'exécuter une fois par environnement, après chaque déploiement initial.

Créer le fichier scripts/grant-sharepoint-mi-permissions.sh¶

#!/bin/bash
# Usage: ./grant-sharepoint-mi-permissions.sh <environment> <sharepoint-site-id>
# Exemple: ./grant-sharepoint-mi-permissions.sh dev 8af7122d-d534-4a93-8063-e1ad30625eaf
# Requis: az login avec un compte Application Administrator dans Entra ID

set -euo pipefail

ENVIRONMENT="${1:?Argument 1 requis: environment (dev|test|prod)}"
SHAREPOINT_SITE_ID="${2:?Argument 2 requis: SharePoint Site ID (format: {hostname},{site-guid},{web-guid})}"
RESOURCE_GROUP="eql-${ENVIRONMENT}-rg"
FUNC_APP_NAME="eql-${ENVIRONMENT}-func"  # À ajuster selon votre convention de nommage

# 1. Récupérer l'Object ID de la Managed Identity du Function App
echo "Recherche du Function App dans ${RESOURCE_GROUP}..."
FUNC_APP=$(az functionapp list --resource-group "$RESOURCE_GROUP" --query '[0].name' -o tsv)
MI_OBJECT_ID=$(az webapp identity show \
  --name "$FUNC_APP" \
  --resource-group "$RESOURCE_GROUP" \
  --query principalId -o tsv)

echo "✓ Managed Identity Object ID: $MI_OBJECT_ID"

# 2. Récupérer l'Object ID du service principal Microsoft Graph
GRAPH_APP_ID="00000003-0000-0000-c000-000000000000"  # Constant universel
GRAPH_SP_ID=$(az ad sp show --id "$GRAPH_APP_ID" --query id -o tsv)
echo "✓ Microsoft Graph SP ID: $GRAPH_SP_ID"

# 3. Accorder Sites.Selected (rôle d'application) à la Managed Identity
# Idempotent: vérifier si déjà accordé avant d'appliquer
echo "Vérification de Sites.Selected..."
SITES_SELECTED_ROLE_ID="883ea226-0bf2-4a8f-9f9d-1a9a364b0ed4"
EXISTING=$(az rest --method GET \
  --url "https://graph.microsoft.com/v1.0/servicePrincipals/${GRAPH_SP_ID}/appRoleAssignedTo" \
  --query "value[?principalId=='${MI_OBJECT_ID}' && appRoleId=='${SITES_SELECTED_ROLE_ID}'].id" \
  -o tsv 2>/dev/null || echo "")

if [ -z "$EXISTING" ]; then
  echo "Accord de Sites.Selected à la Managed Identity..."
  az rest --method POST \
    --url "https://graph.microsoft.com/v1.0/servicePrincipals/${GRAPH_SP_ID}/appRoleAssignedTo" \
    --headers "Content-Type=application/json" \
    --body "{
      \"principalId\": \"${MI_OBJECT_ID}\",
      \"resourceId\": \"${GRAPH_SP_ID}\",
      \"appRoleId\": \"${SITES_SELECTED_ROLE_ID}\"
    }"
  echo "✓ Sites.Selected accordé"
else
  echo "✓ Sites.Selected déjà accordé (skip)"
fi

# 4. Récupérer l'App ID de la Managed Identity
MI_APP_ID=$(az ad sp show --id "$MI_OBJECT_ID" --query appId -o tsv)
echo "✓ Managed Identity App ID: $MI_APP_ID"

# 5. Accorder l'accès write sur le site SharePoint spécifique
echo "Accord de l'accès write sur le site SharePoint ${SHAREPOINT_SITE_ID}..."
az rest --method POST \
  --url "https://graph.microsoft.com/v1.0/sites/${SHAREPOINT_SITE_ID}/permissions" \
  --headers "Content-Type=application/json" \
  --body "{
    \"roles\": [\"write\"],
    \"grantedToIdentitiesV2\": [{
      \"application\": {
        \"id\": \"${MI_APP_ID}\",
        \"displayName\": \"${FUNC_APP}\"
      }
    }]
  }"
echo "✓ Accès write accordé sur le site SharePoint"

echo ""
echo "✅ Migration Managed Identity complétée pour ${ENVIRONMENT}"

9. Rollback — Procédure d'urgence¶

Rollback immédiat (sans redéploiement Bicep) — 2 minutes¶

Si la Managed Identity ne peut pas accéder à SharePoint après la migration :

APPCONFIG_NAME="eql-dev-appconfig"  # À adapter à l'environnement

# 1. Remettre les clés AZURE_* dans App Config
az appconfig kv set --name "$APPCONFIG_NAME" --key "AZURE_TENANT_ID" --value "<tenant-id>" --yes
az appconfig kv set --name "$APPCONFIG_NAME" --key "AZURE_CLIENT_ID" --value "<client-id>" --yes

# 2. AZURE_CLIENT_SECRET : créer manuellement via portail Azure
# App Configuration → Explorer → Créer nouvelle clé
# Type: "Key Vault reference"
# URI: "https://<vault-name>.vault.azure.net/secrets/azure-ad-client-secret/"

# 3. Changer SharePoint:AuthMode vers ClientSecret
az appconfig kv set --name "$APPCONFIG_NAME" --key "SharePoint:AuthMode" --value "ClientSecret" --yes

# 4. Redémarrer le Function App
az functionapp restart --name "eql-dev-func-<uniquestring>" --resource-group "eql-dev-rg"

Rollback complet — Redéploiement Bicep¶

Si le rollback par script échoue, revert le commit Bicep et redéployer via le pipeline CI/CD. Le secret azure-ad-client-secret est conservé dans Key Vault — le rollback est non-destructif.

10. Ce qui reste (et pourquoi c'est acceptable)¶

Ce qui reste Raison Risque
nethris-user-password dans Key Vault (sans expiration forcée) API tierce — Nethris ne supporte pas Entra ID Faible — accès MI uniquement, pas d'exposition à un secret humain
azure-ad-client-secret dans Key Vault pour Easy Auth Géré exclusivement par la plateforme App Service — aucune lecture en code C# Faible — rotation possible sans redéploiement, hors scope applicatif
AZURE_CLIENT_SECRET dans local.settings.json des devs Local uniquement, pour callback OAuth du formulaire SMS — jamais en production Minimal — non committée, chaque dev gère sa propre copie
azure-ad-client-secret dans GitHub Actions secrets Injecté dans le déploiement Bicep pour Easy Auth — toujours nécessaire Minimal — géré via OIDC, rotation possible en KV sans redéploiement

11. Validation post-migration¶

Checklist pour dev¶

Infrastructure : - [ ] SharePoint:AuthMode = ManagedIdentity visible dans App Configuration - [ ] AZURE_CLIENT_SECRET absent de App Configuration - [ ] AZURE_TENANT_ID absent de App Configuration - [ ] AZURE_CLIENT_ID absent de App Configuration - [ ] Sites.Selected accordé à la Managed Identity (vérifier via az rest GET /servicePrincipals/{graphId}/appRoleAssignedTo) - [ ] Accès write accordé sur le site SharePoint dev

Fonctionnel : - [ ] Easy Auth fonctionne — accès à l'app via navigateur → redirect Entra ID login - [ ] MICROSOFT_PROVIDER_AUTHENTICATION_SECRET résolu dans App Settings - [ ] Sync Nethris complète avec succès (GET /api/sync/nethris-reports) - [ ] Au moins 1 fichier uploadé dans SharePoint - [ ] Logs Application Insights montrent succès (pas d'erreurs AuthenticationFailedException)

Appliquer la même checklist après succès sur dev.
