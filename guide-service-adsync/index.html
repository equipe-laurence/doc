Service Windows de synchronisation AD (EquipeLaurence.AdSync)¶

Le service lit la table Azure BaseTi et met à jour les attributs Active Directory autorisés. Un cycle s'exécute toutes les AdSync:ScheduleInterval (1 h par défaut). Un cycle en échec n'arrête pas le service.

Installation¶

  1. Obtenir le paquet : télécharger l'artefact adsync-service-package de l'exécution CI/déploiement (GitHub Actions → Artifacts; le zip téléchargé contient directement EquipeLaurence.AdSync.exe, appsettings.json, install-adsync-service.ps1 et LISEZMOI.md), ou le générer localement avec .\scripts\package-adsync-service.ps1 (produit artifacts\adsync-service.zip). Extraire le tout (ex. D:\Services\AdSync).
  2. Éditer appsettings.json (ou utiliser des variables d'environnement, voir ci-dessous).
  3. En PowerShell élevé, depuis le dossier extrait : .\install-adsync-service.ps1 -BinPath D:\Services\AdSync\EquipeLaurence.AdSync.exe -Account 'DOMAINE\svc-adsync$' (gMSA recommandé).
  4. Valider avec EquipeLaurence.AdSync.exe --simulate (sous le compte du service), puis Start-Service EquipeLaurence.AdSync.

Configuration minimale à renseigner¶

appsettings.json est livré avec des valeurs de remplacement entre chevrons (<...>). Tant qu'elles ne sont pas remplacées, le service refuse de démarrer (code 2) avec un message qui nomme la clé.

Clé Valeur livrée Rôle
AdSync:DomainController <dc01.domaine.local> Nom d'hôte ou IPv4 du contrôleur de domaine (sans port ni schéma)
AdSync:UseLdaps, AdSync:RequireSecureBind true, true Liaison sécurisée (obligatoire pour écrire)
AdSync:AllowedSearchBase <OU=Employes,DC=domaine,DC=local> OU maximale où le service peut lire et écrire
AdSync:MailDomains, AdSync:UpnSuffixes <domaine.com> Domaines reconnus pour le rapprochement des identités
AdSync:MatchOn UserPrincipalName (défaut) Attribut(s) de rapprochement : l'utilisateur est trouvé par son userPrincipalName = <code>@<UpnSuffixes> (son adresse courriel). Options : Mail, SamAccountName, combinables ("UserPrincipalName, Mail")
AdSync:BackupPath, AdSync:ReportPath <D:\Services\AdSync\backup>, <...\reports> Sauvegarde avant écriture et rapports (chemins absolus)
AdSync:AllowedUsers [] Liste du pilote (voir « Déploiement progressif »)
AzureTable:TableServiceUri <https://compte.table.core.windows.net> URI du service Table Azure
AzureTable:AuthMode, AzureTable:TableName DefaultAzureCredential, BaseTi Authentification (DefaultAzureCredential ou AccountKey) et table lue

Connexion à Active Directory¶

Aucun mot de passe : la liaison LDAP utilise l'identité du compte qui exécute le service (Negotiate/Kerberos).

  • Exécuter le service sous un gMSA (-Account 'DOMAINE\svc-adsync$').
  • Déléguer à ce compte la lecture sur l'OU AllowedSearchBase et l'écriture uniquement sur les attributs de AdSync:AllowedAttributes.
  • Utiliser LDAPS (UseLdaps: true) ; RequireSecureBind doit rester à true pour écrire.

Connexion à Azure Table¶

Le service lit la table avec DefaultAzureCredential (identité Entra) par défaut, ou avec la clé du compte de stockage (AccountKey, voir plus bas). Il ne fait aucune écriture.

  • Donner le rôle Storage Table Data Reader sur le compte de stockage à l'identité utilisée.
  • Un service Windows ne voit ni az login ni Visual Studio. Utiliser :
  • une identité managée (Azure Arc ou VM Azure) : aucune configuration supplémentaire ; ou
  • un principal de service : définir AZURE_TENANT_ID, AZURE_CLIENT_ID et AZURE_CLIENT_SECRET (ou un certificat) au niveau machine ou dans l'environnement du service. Ces variables n'utilisent pas le préfixe ADSYNC_.
  • Une erreur 403 AuthorizationPermissionMismatch signifie que l'identité est reconnue mais n'a pas le rôle de données Storage Table Data Reader (Owner ou Contributor ne suffisent pas).

Repli : clé d'accès du compte de stockage (AccountKey)¶

Si l'identité Entra n'est pas utilisable, le service peut s'authentifier avec une clé d'accès du compte de stockage. Exception au principe lecteur : la clé donne un accès complet au compte (le service, lui, ne fait que lire). La faire pivoter après la POC.

  • AzureTable:AuthMode = AccountKey (dans appsettings.json ou ADSYNC_AzureTable__AuthMode).
  • La clé se fournit uniquement par la variable d'environnement ADSYNC_AzureTable__AccountKey, définie pour le service (valeur Environment de la clé de registre HKLM\SYSTEM\CurrentControlSet\Services\EquipeLaurence.AdSync), jamais dans appsettings.json.
  • AzureTable:AccountName est facultatif : il est déduit de TableServiceUri.
  • Une clé absente ou qui n'est pas en base64 empêche le démarrage (code 2) ; la valeur n'est jamais journalisée.

Test en ligne de commande (simulation)¶

EquipeLaurence.AdSync.exe --simulate exécute un seul cycle en simulation puis quitte, sans démarrer le service. Aucune écriture n'est faite, même si ApplyEnabled vaut true. Un résumé est affiché et le code de sortie reflète le résultat (0 = succès, 1 = échecs de traitement, 2 = configuration invalide, 3 = infrastructure, 4 = refus par un garde-fou). Sans l'option, le programme tourne en boucle (console) ou comme service Windows.

Dans une console interactive (--simulate ou exécution en boucle en console), chaque utilisateur ayant au moins un écart est affiché sous forme de tableau ; Nom est le displayName actuel de l'annuaire. Rien n'est affiché lorsque la sortie est redirigée (fichier, tube) ou lorsque le programme s'exécute comme service Windows, afin que les valeurs ne se retrouvent jamais dans un fichier :

UniqueCode: AAlwan
Nom: Adam Alwan
Changements:
| Attribut | Avant     | Après            |
| ======== | ========= | ================ |
| title    | Ingénieur | Chef de division |
  • <<null>> signifie attribut absent (avant) ou effacé (après) ; les valeurs ne sont jamais tronquées.
  • Seuls les attributs configurés "Sensitive": false sont affichés en clair ; les autres apparaissent [masqué]. Les 8 attributs livrés dans appsettings.json sont explicitement Sensitive: false.
  • Hors simulation, une colonne Résultat indique le sort de chaque écriture (écrit et vérifié, échec de vérification, limite atteinte (non écrit), etc.).
  • Ces valeurs ne sont jamais envoyées au journal (journal d'événements Windows, Application Insights) ni aux rapports JSONL, et rien n'est affiché quand le programme tourne comme service Windows.

En cas de code 3, le journal donne la cause sans aucune donnée sensible (ni DN, ni valeur, ni secret), par exemple :

  • Azure Table read failed (status 403, code AuthorizationPermissionMismatch) : l'identité n'a pas le rôle Storage Table Data Reader, ou le mode AccountKey n'est pas activé.
  • Directory access failed (Unavailable, code 81 ServerDown). Connect/bind to dc01:636 (LDAPS, Negotiate as DOMAINE\svc-adsync$) failed: The LDAP server is unavailable. Hint: … : le contrôleur de domaine AdSync:DomainController est injoignable (DNS, réseau/VPN, pare-feu, port 636, certificat LDAPS).

Quand l'annuaire ne peut pas être lu, le journal indique :

  • l'étape : connexion/liaison (Connect/bind), recherche (search), lecture (read) ou écriture (write) ;
  • le serveur, le port, le transport et le compte d'exécution ;
  • le code LDAP et son nom (par exemple 49 InvalidCredentials, 50 InsufficientAccessRights, 10 Referral, 32 NoSuchObject) ;
  • une piste de résolution (Hint:) ;
  • l'utilisateur et l'attribut en cause (ligne Directory could not be read while resolving user … ou … for user …, attribute …).

Pour une connexion ou une liaison refusée, le texte d'erreur du client et du serveur est repris : par exemple data 52e signifie identifiants refusés. Pour les autres opérations, seul le code est conservé, car le texte du serveur peut citer un DN.

Utilisateurs introuvables (UserNotFound)¶

Pour chaque utilisateur introuvable, le journal indique ce qui a été cherché et combien d'entrées l'annuaire a renvoyées, par exemple : User code AAlwan not found: searched userPrincipalName=aalwan@equipelaurence.ca (enabled user accounts under AdSync:AllowedSearchBase); 0 entries returned, none kept.

  • 0 entries returned : aucun compte actif sous l'OU n'a cette valeur exacte. Soit le compte est ailleurs dans l'annuaire (OU différente de AllowedSearchBase), soit son UPN ou son courriel n'a pas la forme <code>@<domaine>.
  • N entries returned, none kept : des comptes ont été trouvés mais écartés. La mention Discarded: donne la raison :
  • outside AllowedSearchBase : le compte est hors de la base de recherche ;
  • not a user account : l'objet n'est pas un compte utilisateur ;
  • account disabled : le compte est désactivé ;
  • userAccountControl not readable by the execution account (treated as disabled) : le compte d'exécution ne peut pas lire l'état du compte. Par sécurité, l'outil le considère alors comme désactivé. Il faut déléguer à ce compte la lecture de userAccountControl (avec givenName, sn, displayName, userPrincipalName, mail et objectGUID) sur l'OU des utilisateurs. Un compte voit toujours son propre userAccountControl, mais pas forcément celui des autres.

Pour voir où est le compte et quelles valeurs il porte, sans l'outil et sans RSAT, depuis un poste du domaine :

$code = 'aalwan'
$s = [adsisearcher]"(&(objectCategory=person)(objectClass=user)(|(sAMAccountName=$code)(mail=$code@*)(userPrincipalName=$code@*)))"
$s.SearchRoot = [adsi]''        # tout le domaine courant
'distinguishedName','userPrincipalName','mail','sAMAccountName','userAccountControl' | ForEach-Object { [void]$s.PropertiesToLoad.Add($_) }
$s.FindAll() | ForEach-Object { $_.Properties | Format-List }

À comparer avec la configuration :

  • le distinguishedName doit se terminer par AdSync:AllowedSearchBase ;
  • le domaine de userPrincipalName (ou de mail) doit figurer dans AdSync:UpnSuffixes (ou AdSync:MailDomains) ;
  • userAccountControl ne doit pas contenir le bit 2 (compte désactivé, exclu par défaut).

Les options --simulate, --backup et --restore exécutent une commande puis quittent ; le service n'est jamais démarré. --backup et --restore ne peuvent pas être combinées (code 2).

Sauvegarde des changements à venir (--backup)¶

EquipeLaurence.AdSync.exe --backup calcule le prochain cycle en lecture seule (mêmes règles que la simulation : liste blanche d'attributs, utilisateurs autorisés, formats) et écrit les changements qui seraient appliqués dans le fichier AdSyncBackup.csv du répertoire courant (le fichier existant est remplacé). Rien n'est écrit dans Active Directory.

Colonne Contenu
UniqueId Code unique de l'employé (celui de la table)
Attribut modifié Nom LDAP de l'attribut
Ancienne valeur Valeur actuelle dans AD (vide = attribut absent)
Nouvelle valeur Valeur qui sera écrite (vide = l'attribut sera vidé)

Seuls les changements à écrire figurent dans le fichier (pas les attributs déjà à jour ni les rejets). Format compatible Excel : UTF-8 avec BOM, séparateur ;, fins de ligne CRLF, guillemets selon la RFC 4180 (champ contenant ;, ", un saut de ligne ou des espaces en début/fin). Pour éviter l'injection de formules, une valeur qui commence par =, +, -, @, une tabulation ou un retour chariot est précédée d'une apostrophe ' ; --restore la retire (une apostrophe n'est retirée que si elle précède, éventuellement après d'autres apostrophes, l'un de ces caractères). Ouvrir le fichier dans Excel pour consultation seulement : un nouvel enregistrement depuis Excel peut le corrompre pour --restore (Excel retire notamment les zéros en tête d'un UniqueId numérique, ex. 000123 devient 123, ce qui vise un autre code ou aucun). S'il faut absolument le modifier, le faire dans un éditeur de texte, ou dans Excel en important les colonnes au format Texte puis en enregistrant au format « CSV UTF-8 (délimité par des virgules) » avec le séparateur ;.

Un nouveau --backup écrase le AdSyncBackup.csv précédent du répertoire courant. Si le fichier précédent est encore utile (ex. pour annuler un cycle déjà appliqué), le copier ailleurs (ou le renommer) avant de relancer --backup. Si --backup échoue ou est interrompu (Ctrl+C), le fichier partiel est supprimé.

La console affiche le chemin du fichier et le nombre de lignes. Code de sortie : 0 = succès, 1 = le fichier n'a pas pu être écrit, 2 = schéma de table invalide, 3 = Azure ou AD indisponible.

Attention — données personnelles en clair. Ce fichier contient les valeurs des attributs (ex. dates de naissance) en clair. C'est une exception documentée et approuvée à la règle G13 (« aucune valeur dans les journaux ni les rapports ») : les valeurs ne vont jamais dans les journaux ni dans les rapports JSONL, seulement dans ce fichier. Le générer dans un dossier à accès restreint, ne pas le transmettre par courriel et le supprimer dès qu'il n'est plus nécessaire.

Restauration des anciennes valeurs (--restore)¶

EquipeLaurence.AdSync.exe --restore <fichier.csv> [--simulate] remet la colonne Ancienne valeur de chaque ligne d'un fichier produit par --backup (vide = l'attribut est vidé, seulement si AllowClear est vrai pour cet attribut).

  • Validation du fichier : l'en-tête doit être exactement UniqueId;Attribut modifié;Ancienne valeur;Nouvelle valeur ; une ligne mal formée, un UniqueId ou un attribut vide, ou un même couple (utilisateur, attribut) en double (après normalisation du code) fait refuser tout le fichier (code 2, rien n'est écrit). Un fichier absent ou illisible, ou l'option sans nom de fichier, donne aussi le code 2. Le message indique le numéro de ligne, jamais une valeur.
  • Écriture ou simulation : les écritures n'ont lieu que si AdSync:ApplyEnabled vaut true et que --simulate est absent. Sinon, la commande indique seulement ce qui serait fait.
  • Garde-fous conservés : identité d'exécution (G15, en mode écriture), liste blanche et liste d'interdits d'attributs, validation du format de la valeur à remettre (c'est la valeur normalisée qui est écrite, ex. espaces et sauts de ligne en début/fin retirés pour les formats Text et Regex ; une valeur refusée par le format donne InvalidValue), AllowClear respecté (une Ancienne valeur vide n'est remise que si AllowClear est vrai pour l'attribut, sinon la ligne est rejetée avec InvalidValue), AllowedUsers (sauf AllowAllUsers, même normalisation des codes que la synchronisation), utilisateurs désactivés exclus sauf IncludeDisabled, résolution de l'utilisateur dans l'OU autorisée (AllowedSearchBase).
  • Contrôle de conflit : la valeur actuelle dans AD doit être égale à la Nouvelle valeur du fichier (vide = attribut absent). Sinon la ligne est ignorée avec la raison Conflict (quelqu'un a modifié la valeur depuis). Si la valeur actuelle est déjà l'Ancienne valeur, la ligne est AlreadyUpToDate.
  • Chaque écriture est précédée d'une sauvegarde DPAPI (AdSync:BackupPath ; en cas d'échec, rien n'est écrit pour cette ligne) puis vérifiée par relecture. Chaque résultat et le résumé vont dans le rapport JSONL (AdSync:ReportPath), sans valeur.
  • Disjoncteurs contournés : MaxWritesPerRun, MaxClearsPerRun et MaxDiffPercent ne s'appliquent pas à --restore, qui est une reprise explicite de l'opérateur. Simuler d'abord.

Un résumé est affiché (mode=dry-run|apply, lignes traitées, écrites, à jour, rejetées, en échec). Code de sortie : 0 = succès (y compris lignes rejetées ou en conflit), 1 = au moins un échec (sauvegarde, écriture, vérification), 2 = fichier ou arguments invalides, 4 = refus par la garde d'identité.

Exemple de reprise¶

Arrêter le service avant de restaurer. Tant que la table source contient les mêmes valeurs, chaque cycle du service réapplique la Nouvelle valeur : une restauration faite pendant que le service tourne est annulée au cycle suivant. Avant de redémarrer le service, corriger la cause : corriger la table source, ou retirer l'utilisateur de AllowedUsers, ou remettre AdSync:ApplyEnabled à false. --restore n'écrit que si ApplyEnabled vaut true : ne passer ApplyEnabled à false qu'après la restauration.

cd D:\Securise\AdSync                                   # dossier à accès restreint
D:\Services\AdSync\EquipeLaurence.AdSync.exe --backup   # 1. AdSyncBackup.csv : changements à venir
# 2. Le service applique les changements (ApplyEnabled = true) au prochain cycle.
# 3. Pour annuler : arrêter le service, simuler, puis restaurer.
Stop-Service EquipeLaurence.AdSync
D:\Services\AdSync\EquipeLaurence.AdSync.exe --restore .\AdSyncBackup.csv --simulate
D:\Services\AdSync\EquipeLaurence.AdSync.exe --restore .\AdSyncBackup.csv
# 4. Corriger la table source, OU retirer l'utilisateur de AllowedUsers, OU mettre ApplyEnabled = false,
#    sinon le prochain cycle réapplique la « Nouvelle valeur ». Puis redémarrer le service.
Start-Service EquipeLaurence.AdSync
Remove-Item .\AdSyncBackup.csv                          # 5. Supprimer le fichier

Déploiement progressif¶

  1. Simulation : AdSync:ApplyEnabled = false (défaut). Chaque cycle calcule les changements et les journalise sans rien écrire. Vérifier les rapports.
  2. Pilote : renseigner AdSync:AllowedUsers (liste restreinte) puis ApplyEnabled = true.
  3. Généralisation : AdSync:AllowAllUsers = true après validation du pilote.

Disjoncteurs¶

  • MaxUsersPerRun, MaxWritesPerRun, MaxClearsPerRun (défaut : 1 chacun, à relever après le pilote) : un cycle qui dépasse une limite s'arrête sans écrire.
  • MaxDiffPercent / MaxDiffMinPopulation : refus du cycle si la table diffère trop de l'état précédent.
  • Une valeur vide dans la table ne vide un attribut que si AllowClear est vrai pour cet attribut.

Attributs étendus (dates de naissance et d'embauche)¶

Les deux dates sont écrites dans des attributs d'extension natifs d'Active Directory, déclarés dans AdSync:AllowedAttributes (appsettings.json) :

Champ Nethris Colonne de la table Attribut AD AllowClear
Date d'embauche HireDate msDS-cloudExtensionAttribute1 false
Date de naissance BirthDate msDS-cloudExtensionAttribute2 true 
{ "Name": "msDS-cloudExtensionAttribute1", "Format": "IsoDate", "TableColumn": "HireDate", "MinAgeYears": 0, "AllowClear": false, "Sensitive": false },
{ "Name": "msDS-cloudExtensionAttribute2", "Format": "IsoDate", "TableColumn": "BirthDate", "AllowClear": true, "Sensitive": false }
  • Format IsoDate : seule une date yyyy-MM-dd passée est acceptée ; une valeur illisible est rejetée (InvalidValue) sans rien écrire. La date de naissance doit en plus correspondre à un âge de 14 à 100 ans (défaut).
  • BirthDate n'est renseignée dans la table que si l'employé publie sa date d'anniversaire. Quand la colonne est vide (consentement retiré), l'attribut AD est effacé.
  • Une HireDate vide n'efface jamais l'attribut AD : l'écart est rejeté (SourceEmpty) et la valeur existante est conservée.
  • Les deux valeurs sont affichées en clair dans la console interactive (Sensitive: false).
  • Le gMSA du service doit avoir le droit d'écriture sur ces deux attributs, sur les OU des employés seulement.

Variables d'environnement¶

Les clés se surchargent avec le préfixe ADSYNC_ et __ comme séparateur (ex. ADSYNC_AdSync__ApplyEnabled=true).

AdSync:LocalDirectory:Path (simulation avec un annuaire local en JSON, pour le développement sans contrôleur de domaine) doit rester vide sur le serveur : s'il est défini, Active Directory n'est jamais contacté. Lancé comme service Windows, le programme refuse alors de démarrer (code 2).
