Service Windows de synchronisation AD (EquipeLaurence.AdSync)¶

Procédure d'installation et d'exploitation pas à pas : Service AdSync — Installation et exploitation. Cette page est la référence (options, garde-fous, commandes).

Le service lit la table Azure BaseTi et met à jour les attributs Active Directory autorisés. Un cycle s'exécute toutes les AdSync:ScheduleInterval (1 h par défaut). Un cycle en échec n'arrête pas le service.

Installation¶

  1. Obtenir le paquet : télécharger l'artefact adsync-service-package de l'exécution CI/déploiement (GitHub Actions → Artifacts; le zip téléchargé contient directement EquipeLaurence.AdSync.exe, appsettings.json, install-adsync-service.ps1 et LISEZMOI.md), ou le générer localement avec .\scripts\package-adsync-service.ps1 (produit artifacts\adsync-service.zip). Extraire le tout (ex. D:\Services\AdSync).
  2. Éditer appsettings.json (ou utiliser des variables d'environnement, voir ci-dessous).
  3. En PowerShell élevé, depuis le dossier extrait : .\install-adsync-service.ps1 -BinPath D:\Services\AdSync\EquipeLaurence.AdSync.exe -Account 'DOMAINE\svc-adsync$' (gMSA recommandé).
  4. Valider avec EquipeLaurence.AdSync.exe --simulate (sous le compte du service), puis Start-Service EquipeLaurence.AdSync.

Configuration minimale à renseigner¶

Les valeurs de remplacement entre chevrons (<...>) font refuser le démarrage (code 2) avec un message qui nomme la clé. Le appsettings.json actuellement livré contient toutefois les valeurs de l'environnement EQL, dont ApplyEnabled: true et AllowAllUsers: true : vérifier chaque clé avant le premier démarrage (voir le guide d'installation, section 5). La colonne « Valeur livrée » ci-dessous donne les valeurs modèles.

Clé Valeur livrée Rôle
AdSync:DomainController <dc01.domaine.local> Nom d'hôte ou IPv4 du contrôleur de domaine (sans port ni schéma)
AdSync:UseLdaps, AdSync:RequireSecureBind true, true Liaison sécurisée (obligatoire pour écrire)
AdSync:AllowedSearchBase <OU=Employes,DC=domaine,DC=local> OU maximale où le service peut lire et écrire
AdSync:MailDomains, AdSync:UpnSuffixes <domaine.com> Domaines reconnus pour le rapprochement des identités
AdSync:MatchOn UserPrincipalName (défaut) Attribut(s) de rapprochement : l'utilisateur est trouvé par son userPrincipalName = <code>@<UpnSuffixes> (son adresse courriel). Options : Mail, SamAccountName, combinables ("UserPrincipalName, Mail")
AdSync:BackupPath, AdSync:ReportPath <D:\Services\AdSync\backup>, <...\reports> Sauvegarde avant écriture et rapports (chemins absolus)
AdSync:AllowedUsers [] Liste du pilote (voir « Déploiement progressif »)
AdSync:ExcludedUsers [] Codes jamais synchronisés ni restaurés (ex. ["JFArbique"]) ; prioritaire sur AllowedUsers et AllowAllUsers ; voir « Exclure des utilisateurs »
AzureTable:TableServiceUri <https://compte.table.core.windows.net> URI du service Table Azure
AzureTable:AuthMode, AzureTable:TableName DefaultAzureCredential, BaseTi Authentification (DefaultAzureCredential ou AccountKey) et table lue
AzureTable:OfficeAddressTableName OfficeAddress (défaut du code) Table des adresses de bureaux (lecture seule, jamais créée) ; voir « Adresses des bureaux »

Connexion à Active Directory¶

Aucun mot de passe : la liaison LDAP utilise l'identité du compte qui exécute le service (Negotiate/Kerberos).

  • Exécuter le service sous un gMSA (-Account 'DOMAINE\svc-adsync$').
  • Déléguer à ce compte la lecture sur l'OU AllowedSearchBase et l'écriture uniquement sur les attributs de AdSync:AllowedAttributes. Le script scripts\initialize-adsync-service-account.ps1 crée le gMSA et pose cette délégation attribut par attribut : voir Préparation du compte de service et des accès.
  • Utiliser LDAPS (UseLdaps: true) ; RequireSecureBind doit rester à true pour écrire.

Identité d'exécution (G15)¶

Avant toute écriture (cycle avec ApplyEnabled, --restore, --attribute), l'outil journalise le nom du compte qui l'exécute et le classe d'après ses SID (jamais d'après son nom) : compte privilégié (membre des Administrateurs, Admins du domaine, Administrateurs de l'entreprise, Opérateurs de compte/serveur/sauvegarde/impression, etc.) et compte système ou machine (SYSTEM, LocalService, NetworkService, compte d'un contrôleur de domaine). Une simulation (--simulate, --backup, --restore … --simulate, --attribute … --simulate) est toujours autorisée.

Aucune question n'est posée à l'opérateur : la décision ne dépend que du compte et de la configuration, en console comme en service Windows.

Compte d'exécution Décision
Compte délégué ordinaire (gMSA, compte de service) Écrit
Compte privilégié (ex. administrateur du domaine) Refusé (code 4), sauf AdSync:AllowPrivilegedIdentity
SYSTEM, compte de service intégré, compte machine du DC Refusé (code 4), sans exception

Un compte privilégié refusé obtient Execution identity EQL\utilisateur (privileged: True, system or machine: False): Refused. puis Run … refused by the execution identity guard (code 4) ; --simulate fonctionne toujours. Le journal ne contient jamais de SID ni de valeur.

Le service Windows s'exécute sous un compte dédié et délégué : le gMSA EQL\Svc-AdSync$, qui n'a que la lecture sur AllowedSearchBase et l'écriture sur les attributs de AdSync:AllowedAttributes. Ce compte n'est pas privilégié : il écrit sans autre formalité et le service ne se bloque sur aucune question.

Un administrateur qui veut écrire depuis une console utilise un compte délégué (par exemple en lançant l'outil sous le gMSA ou un compte de service équivalent). En dernier recours seulement, et avec une justification consignée (dérogation approuvée, durée limitée), ADSYNC_AdSync__AllowPrivilegedIdentity=true autorise un compte privilégié ; SYSTEM et les comptes machine restent toujours refusés.

Limite connue : la classification lit les groupes actifs du jeton Windows. Dans une console PowerShell non élevée (UAC), les groupes d'administration sont filtrés : un administrateur peut alors être classé « non privilégié » et écrire, avec ses droits Kerberos complets. Lancer l'outil sous le compte délégué prévu reste la règle.

Connexion à Azure Table¶

Le service lit la table avec DefaultAzureCredential (identité Entra) par défaut, ou avec la clé du compte de stockage (AccountKey, voir plus bas). Il ne fait aucune écriture.

  • Donner le rôle Storage Table Data Reader à l'identité utilisée, de préférence sur les seules tables (…/tableServices/default/tables/BaseTi et …/tables/OfficeAddress) plutôt que sur tout le compte de stockage.
  • Un service Windows ne voit ni az login ni Visual Studio. Utiliser :
  • une identité managée (Azure Arc ou VM Azure) : aucune configuration supplémentaire ; ou
  • un principal de service : définir AZURE_TENANT_ID, AZURE_CLIENT_ID et AZURE_CLIENT_CERTIFICATE_PATH (fichier PFX ou PEM ; à défaut AZURE_CLIENT_SECRET) au niveau machine ou dans l'environnement du service. Ces variables n'utilisent pas le préfixe ADSYNC_. Les scripts new-adsync-certificate.ps1 et new-adsync-entra-app.ps1 préparent le certificat, l'application et le rôle : voir Préparation du compte de service et des accès.
  • Une erreur 403 AuthorizationPermissionMismatch signifie que l'identité est reconnue mais n'a pas le rôle de données Storage Table Data Reader (Owner ou Contributor ne suffisent pas).

Repli : clé d'accès du compte de stockage (AccountKey)¶

Si l'identité Entra n'est pas utilisable, le service peut s'authentifier avec une clé d'accès du compte de stockage. Exception au principe lecteur : la clé donne un accès complet au compte (le service, lui, ne fait que lire). La faire pivoter après la POC.

  • AzureTable:AuthMode = AccountKey (dans appsettings.json ou ADSYNC_AzureTable__AuthMode).
  • La clé se fournit uniquement par la variable d'environnement ADSYNC_AzureTable__AccountKey, définie pour le service (valeur Environment de la clé de registre HKLM\SYSTEM\CurrentControlSet\Services\EquipeLaurence.AdSync), jamais dans appsettings.json.
  • AzureTable:AccountName est facultatif : il est déduit de TableServiceUri.
  • Une clé absente ou qui n'est pas en base64 empêche le démarrage (code 2) ; la valeur n'est jamais journalisée.

Test en ligne de commande (simulation)¶

EquipeLaurence.AdSync.exe --simulate exécute un seul cycle en simulation puis quitte, sans démarrer le service. Aucune écriture n'est faite, même si ApplyEnabled vaut true. Un résumé est affiché et le code de sortie reflète le résultat (0 = succès, 1 = échecs de traitement, 2 = configuration invalide, 3 = infrastructure, 4 = refus par un garde-fou). Sans l'option, le programme tourne en boucle (console) ou comme service Windows.

Dans une console interactive (--simulate ou exécution en boucle en console), chaque utilisateur ayant au moins un écart est affiché sous forme de tableau ; Nom est le displayName actuel de l'annuaire. Rien n'est affiché lorsque la sortie est redirigée (fichier, tube) ou lorsque le programme s'exécute comme service Windows, afin que les valeurs ne se retrouvent jamais dans un fichier :

UniqueCode: AAlwan
Nom: Adam Alwan
Changements:
| Attribut | Avant     | Après            |
| ======== | ========= | ================ |
| title    | Ingénieur | Chef de division |
  • <<null>> signifie attribut absent (avant) ou effacé (après) ; les valeurs ne sont jamais tronquées.
  • Seuls les attributs configurés "Sensitive": false sont affichés en clair ; les autres apparaissent [masqué]. Les 8 attributs livrés dans appsettings.json sont explicitement Sensitive: false.
  • Hors simulation, une colonne Résultat indique le sort de chaque écriture (écrit et vérifié, échec de vérification, limite atteinte (non écrit), etc.).
  • Une colonne Détail s'ajoute dès qu'une ligne a un refus ou un échec à expliquer (voir « Détail des échecs et des refus »). Les valeurs avant/après restent affichées pour tous les statuts, y compris les échecs (les attributs sensibles restent [masqué]).
  • Un utilisateur exclu (AdSync:ExcludedUsers) apparaît sur une ligne * avec le résultat exclu de la synchronisation.
  • Ces valeurs ne sont jamais envoyées au journal (journal d'événements Windows, Application Insights) ni aux rapports HTML, et rien n'est affiché quand le programme tourne comme service Windows.

Détail des échecs et des refus¶

Chaque refus ou échec porte un détail « étape + code + message » (colonne Détail de la console et du rapport HTML), de la forme Écriture [code 50 InsufficientAccessRights] : L'annuaire a refusé ou n'a pas pu exécuter l'opération.

  • Politique : utilisateur exclu (ExcludedUsers), compte désactivé sans IncludeDisabled.
  • Résolution : compte introuvable, ambigu ou identité non concordante.
  • Source : ligne absente ou dupliquée dans la table, colonne vide (le message nomme la colonne et l'attribut).
  • Validation : valeur de la table refusée par le format de l'attribut (le message nomme la colonne et l'attribut).
  • Sauvegarde : la sauvegarde a échoué, rien n'a été écrit.
  • Écriture : l'annuaire a refusé l'écriture ; le code LDAP (numéro et nom) est affiché quand l'annuaire a répondu.
  • Vérification : la relecture diffère de la valeur écrite, ou la relecture a échoué (code LDAP si disponible).

Le détail ne contient jamais de DN, d'URL ni de valeur d'attribut : seulement des noms de colonnes ou d'attributs, un type d'erreur et un code LDAP.

Exclure des utilisateurs (AdSync:ExcludedUsers)¶

AdSync:ExcludedUsers (liste de codes, par exemple ["JFArbique"]) retire des utilisateurs de toute action. Les codes sont normalisés comme AllowedUsers (casse ignorée, CodeNormalization). L'exclusion est prioritaire : un code présent dans ExcludedUsers et AllowedUsers (ou avec AllowAllUsers = true) est ignoré.

  • Synchronisation : l'utilisateur n'est pas résolu dans l'annuaire, rien n'est lu ni écrit ; il apparaît comme une ligne « exclu de la synchronisation » dans la console et le rapport HTML (raison Excluded, compté dans les rejetés du résumé).
  • Il n'entre pas dans la population du disjoncteur MaxDiffPercent ni dans MaxUsersPerRun/MaxWritesPerRun.
  • --attribute : refusé (code 4) ; --restore : la ligne est ignorée avec la raison Excluded.
  • Une entrée vide ou blanche est refusée au démarrage (code 2).

En cas de code 3, le journal donne la cause sans aucune donnée sensible (ni DN, ni valeur, ni secret), par exemple :

  • Azure Table read failed (status 403, code AuthorizationPermissionMismatch) : l'identité n'a pas le rôle Storage Table Data Reader, ou le mode AccountKey n'est pas activé.
  • Directory access failed (Unavailable, code 81 ServerDown). Connect/bind to dc01:636 (LDAPS, Negotiate as DOMAINE\svc-adsync$) failed: The LDAP server is unavailable. Hint: … : le contrôleur de domaine AdSync:DomainController est injoignable (DNS, réseau/VPN, pare-feu, port 636, certificat LDAPS).

Quand l'annuaire ne peut pas être lu, le journal indique :

  • l'étape : connexion/liaison (Connect/bind), recherche (search), lecture (read) ou écriture (write) ;
  • le serveur, le port, le transport et le compte d'exécution ;
  • le code LDAP et son nom (par exemple 49 InvalidCredentials, 50 InsufficientAccessRights, 10 Referral, 32 NoSuchObject) ;
  • une piste de résolution (Hint:) ;
  • l'utilisateur et l'attribut en cause (ligne Directory could not be read while resolving user … ou … for user …, attribute …).

Pour une connexion ou une liaison refusée, le texte d'erreur du client et du serveur est repris : par exemple data 52e signifie identifiants refusés. Pour les autres opérations, seul le code est conservé, car le texte du serveur peut citer un DN.

Utilisateurs introuvables (UserNotFound)¶

Pour chaque utilisateur introuvable, le journal indique ce qui a été cherché et combien d'entrées l'annuaire a renvoyées, par exemple : User code AAlwan not found: searched userPrincipalName=aalwan@equipelaurence.ca (enabled user accounts under AdSync:AllowedSearchBase); 0 entries returned, none kept.

  • 0 entries returned : aucun compte actif sous l'OU n'a cette valeur exacte. Soit le compte est ailleurs dans l'annuaire (OU différente de AllowedSearchBase), soit son UPN ou son courriel n'a pas la forme <code>@<domaine>.
  • N entries returned, none kept : des comptes ont été trouvés mais écartés. La mention Discarded: donne la raison :
  • outside AllowedSearchBase : le compte est hors de la base de recherche ;
  • not a user account : l'objet n'est pas un compte utilisateur ;
  • account disabled : le compte est désactivé ;
  • userAccountControl not readable by the execution account (treated as disabled) : le compte d'exécution ne peut pas lire l'état du compte. Par sécurité, l'outil le considère alors comme désactivé. Il faut déléguer à ce compte la lecture de userAccountControl (avec givenName, sn, displayName, userPrincipalName, mail et objectGUID) sur l'OU des utilisateurs. Un compte voit toujours son propre userAccountControl, mais pas forcément celui des autres.

Pour voir où est le compte et quelles valeurs il porte, sans l'outil et sans RSAT, depuis un poste du domaine :

$code = 'aalwan'
$s = [adsisearcher]"(&(objectCategory=person)(objectClass=user)(|(sAMAccountName=$code)(mail=$code@*)(userPrincipalName=$code@*)))"
$s.SearchRoot = [adsi]''        # tout le domaine courant
'distinguishedName','userPrincipalName','mail','sAMAccountName','userAccountControl' | ForEach-Object { [void]$s.PropertiesToLoad.Add($_) }
$s.FindAll() | ForEach-Object { $_.Properties | Format-List }

À comparer avec la configuration :

  • le distinguishedName doit se terminer par AdSync:AllowedSearchBase ;
  • le domaine de userPrincipalName (ou de mail) doit figurer dans AdSync:UpnSuffixes (ou AdSync:MailDomains) ;
  • userAccountControl ne doit pas contenir le bit 2 (compte désactivé, exclu par défaut).

Les options --simulate, --backup, --restore et --attribute exécutent une commande puis quittent ; le service n'est jamais démarré. --backup, --restore et --attribute ne peuvent pas être combinées (code 2).

Sauvegarde des changements à venir (--backup)¶

EquipeLaurence.AdSync.exe --backup calcule le prochain cycle en lecture seule (mêmes règles que la simulation : liste blanche d'attributs, utilisateurs autorisés, formats) et écrit les changements qui seraient appliqués dans le fichier AdSyncBackup.csv du répertoire courant (le fichier existant est remplacé). Rien n'est écrit dans Active Directory.

Colonne Contenu
UniqueId Code unique de l'employé (celui de la table)
Attribut modifié Nom LDAP de l'attribut
Ancienne valeur Valeur actuelle dans AD (vide = attribut absent)
Nouvelle valeur Valeur qui sera écrite (vide = l'attribut sera vidé)

Seuls les changements à écrire figurent dans le fichier (pas les attributs déjà à jour ni les rejets). Format compatible Excel : UTF-8 avec BOM, séparateur ;, fins de ligne CRLF, guillemets selon la RFC 4180 (champ contenant ;, ", un saut de ligne ou des espaces en début/fin). Pour éviter l'injection de formules, une valeur qui commence par =, +, -, @, une tabulation ou un retour chariot est précédée d'une apostrophe ' ; --restore la retire (une apostrophe n'est retirée que si elle précède, éventuellement après d'autres apostrophes, l'un de ces caractères). Ouvrir le fichier dans Excel pour consultation seulement : un nouvel enregistrement depuis Excel peut le corrompre pour --restore (Excel retire notamment les zéros en tête d'un UniqueId numérique, ex. 000123 devient 123, ce qui vise un autre code ou aucun). S'il faut absolument le modifier, le faire dans un éditeur de texte, ou dans Excel en important les colonnes au format Texte puis en enregistrant au format « CSV UTF-8 (délimité par des virgules) » avec le séparateur ;.

Un nouveau --backup écrase le AdSyncBackup.csv précédent du répertoire courant. Si le fichier précédent est encore utile (ex. pour annuler un cycle déjà appliqué), le copier ailleurs (ou le renommer) avant de relancer --backup. Si --backup échoue ou est interrompu (Ctrl+C), le fichier partiel est supprimé.

La console affiche le chemin du fichier et le nombre de lignes. Code de sortie : 0 = succès, 1 = le fichier n'a pas pu être écrit, 2 = schéma de table invalide, 3 = Azure ou AD indisponible.

Attention — données personnelles en clair. Ce fichier contient les valeurs des attributs (ex. dates de naissance) en clair. C'est une exception documentée et approuvée à la règle G13 (« aucune valeur dans les journaux ni les rapports ») : les valeurs ne vont jamais dans les journaux ni dans les rapports HTML, seulement dans ce fichier. Le générer dans un dossier à accès restreint, ne pas le transmettre par courriel et le supprimer dès qu'il n'est plus nécessaire.

Restauration des anciennes valeurs (--restore)¶

EquipeLaurence.AdSync.exe --restore <fichier.csv> [--simulate] remet la colonne Ancienne valeur de chaque ligne d'un fichier produit par --backup (vide = l'attribut est vidé, seulement si AllowClear est vrai pour cet attribut).

  • Validation du fichier : l'en-tête doit être exactement UniqueId;Attribut modifié;Ancienne valeur;Nouvelle valeur ; une ligne mal formée, un UniqueId ou un attribut vide, ou un même couple (utilisateur, attribut) en double (après normalisation du code) fait refuser tout le fichier (code 2, rien n'est écrit). Un fichier absent ou illisible, ou l'option sans nom de fichier, donne aussi le code 2. Le message indique le numéro de ligne, jamais une valeur.
  • Écriture ou simulation : les écritures n'ont lieu que si AdSync:ApplyEnabled vaut true et que --simulate est absent. Sinon, la commande indique seulement ce qui serait fait.
  • Garde-fous conservés : identité d'exécution (G15, en mode écriture ; un compte privilégié est refusé sauf AllowPrivilegedIdentity, voir « Identité d'exécution (G15) »), liste blanche et liste d'interdits d'attributs, validation du format de la valeur à remettre (c'est la valeur normalisée qui est écrite, ex. espaces et sauts de ligne en début/fin retirés pour les formats Text et Regex ; une valeur refusée par le format donne InvalidValue), AllowClear respecté (une Ancienne valeur vide n'est remise que si AllowClear est vrai pour l'attribut, sinon la ligne est rejetée avec InvalidValue), AllowedUsers (sauf AllowAllUsers, même normalisation des codes que la synchronisation ; ExcludedUsers est prioritaire : la ligne est ignorée avec la raison Excluded), utilisateurs désactivés exclus sauf IncludeDisabled, résolution de l'utilisateur dans l'OU autorisée (AllowedSearchBase).
  • Contrôle de conflit : la valeur actuelle dans AD doit être égale à la Nouvelle valeur du fichier (vide = attribut absent). Sinon la ligne est ignorée avec la raison Conflict (quelqu'un a modifié la valeur depuis). Si la valeur actuelle est déjà l'Ancienne valeur, la ligne est AlreadyUpToDate.
  • Chaque écriture est précédée d'une sauvegarde DPAPI (AdSync:BackupPath ; en cas d'échec, rien n'est écrit pour cette ligne) puis vérifiée par relecture. Les lignes modifiées ou en erreur et un résumé vont dans un rapport HTML <ReportPath>\AAAA-MM-JJ-hh-mm-ss.html (heure locale du début de l'exécution), généré uniquement s'il y a au moins un changement, un échec ou un rejet (sinon aucun fichier), sans aucune valeur. À l'écriture d'un nouveau rapport, les rapports plus vieux que AdSync:ReportRetentionDays (30 jours par défaut, minimum 1) sont supprimés.
  • Disjoncteurs contournés : MaxWritesPerRun, MaxClearsPerRun et MaxDiffPercent ne s'appliquent pas à --restore, qui est une reprise explicite de l'opérateur. Simuler d'abord.

Un résumé est affiché (mode=dry-run|apply, lignes traitées, écrites, à jour, rejetées, en échec). Code de sortie : 0 = succès (y compris lignes rejetées ou en conflit), 1 = au moins un échec (sauvegarde, écriture, vérification), 2 = fichier ou arguments invalides, 4 = refus par la garde d'identité.

Exemple de reprise¶

Arrêter le service avant de restaurer. Tant que la table source contient les mêmes valeurs, chaque cycle du service réapplique la Nouvelle valeur : une restauration faite pendant que le service tourne est annulée au cycle suivant. Avant de redémarrer le service, corriger la cause : corriger la table source, ou retirer l'utilisateur de AllowedUsers, ou remettre AdSync:ApplyEnabled à false. --restore n'écrit que si ApplyEnabled vaut true : ne passer ApplyEnabled à false qu'après la restauration.

cd D:\Securise\AdSync                                   # dossier à accès restreint
D:\Services\AdSync\EquipeLaurence.AdSync.exe --backup   # 1. AdSyncBackup.csv : changements à venir
# 2. Le service applique les changements (ApplyEnabled = true) au prochain cycle.
# 3. Pour annuler : arrêter le service, simuler, puis restaurer.
Stop-Service EquipeLaurence.AdSync
D:\Services\AdSync\EquipeLaurence.AdSync.exe --restore .\AdSyncBackup.csv --simulate
D:\Services\AdSync\EquipeLaurence.AdSync.exe --restore .\AdSyncBackup.csv
# 4. Corriger la table source, OU retirer l'utilisateur de AllowedUsers, OU mettre ApplyEnabled = false,
#    sinon le prochain cycle réapplique la « Nouvelle valeur ». Puis redémarrer le service.
Start-Service EquipeLaurence.AdSync
Remove-Item .\AdSyncBackup.csv                          # 5. Supprimer le fichier

Mise à jour manuelle d'un attribut (--attribute)¶

Pour tester une écriture dans Active Directory sans lire la table Azure (aucun appel à Azure Table n'est fait) :

EquipeLaurence.AdSync.exe --attribute <nom> --value <valeur> --user <UniqueCode> [--simulate]
  • Les trois options sont obligatoires, une seule fois chacune, dans n'importe quel ordre. Une option sans valeur, une valeur qui commence par --, un attribut ou un code vide affichent l'usage (code 2). Combinée avec --backup ou --restore : code 2.
  • Écriture systématique : la commande écrit même si AdSync:ApplyEnabled vaut false, sauf avec --simulate (aucune écriture, simple comparaison). Comme --restore, c'est une action explicite de l'opérateur : MaxWritesPerRun, MaxClearsPerRun et MaxDiffPercent ne s'appliquent pas.
  • Garde d'identité (G15) : appliquée en écriture : un compte privilégié est refusé (code 4) sauf AllowPrivilegedIdentity (voir plus haut). SYSTEM et les comptes machine sont toujours refusés.
  • Attribut : il doit figurer dans AdSync:AllowedAttributes avec AllowManualSet vrai (défaut) et Sensitive: false (une valeur sensible n'est jamais acceptée en ligne de commande) ; la liste d'interdits (G16) s'applique. Le nom est insensible à la casse. Sinon : code 2 et la liste des attributs autorisés.
  • Valeur : même validation que la synchronisation (format IsoDate = yyyy-MM-dd avec la plage d'âge configurée, Text = texte sans saut de ligne ni caractère de contrôle de MaxLength caractères au plus, Regex). La valeur normalisée est écrite (espaces de début et de fin retirés). Il n'y a pas de dérivation (FullName, MobileIfShared) : la valeur donnée est écrite telle quelle. Valeur refusée : code 2.
  • Valeur vide (--value "") : efface l'attribut seulement si AllowClear est vrai pour lui, comme une valeur vide de la table ; sinon code 2. Dans PowerShell 7.3 ou plus, --value "" transmet bien une chaîne vide ; avec Windows PowerShell 5.1, utiliser --value '""'.
  • Utilisateur : résolu exactement comme par la synchronisation (AllowedSearchBase, MatchOn, UpnSuffixes, MailDomains, normalisation du code CodeNormalization (voir « Normalisation du code unique »), contrôleur DomainController, contrôle de cohérence d'identité). Le code doit figurer dans AdSync:AllowedUsers, sauf AllowAllUsers (sinon code 4). Un code listé dans AdSync:ExcludedUsers est refusé (code 4) même s'il est autorisé. Un compte désactivé est refusé sauf IncludeDisabled (code 4). Utilisateur introuvable, ambigu (plusieurs comptes) ou incohérent : code 1, rien n'est écrit (le journal donne la configuration de rapprochement et la recherche faite, voir « Utilisateurs introuvables »).
  • Écriture : sauvegarde DPAPI préalable (AdSync:BackupPath), écriture, vérification par relecture, rapport HTML (<ReportPath>\AAAA-MM-JJ-hh-mm-ss.html, mode Manual, généré seulement s'il y a un changement, un échec ou un rejet), sans aucune valeur dans le journal ni le rapport.

La console interactive affiche le même tableau Avant / Après que la simulation (avec la colonne Résultat en écriture), puis une ligne de résumé :

Manual update 3f2c…: mode=apply attribute=msDS-cloudExtensionAttribute2 user=AAlwan written=1 upToDate=0 failed=0 exitCode=Success

Code de sortie : 0 = écrit, déjà à jour ou simulé ; 1 = utilisateur introuvable/ambigu ou échec (sauvegarde, écriture, vérification) ; 2 = arguments, attribut ou valeur invalides ; 3 = annuaire indisponible ; 4 = refus par un garde-fou (identité d'exécution, AllowedUsers, compte désactivé).

cd D:\Services\AdSync
# 1. Comparer sans écrire
.\EquipeLaurence.AdSync.exe --attribute msDS-cloudExtensionAttribute2 --value 1985-04-12 --user AAlwan --simulate
# 2. Écrire (sous un compte délégué ; un compte privilégié est refusé, code 4)
.\EquipeLaurence.AdSync.exe --attribute msDS-cloudExtensionAttribute2 --value 1985-04-12 --user AAlwan
# 3. Exemple texte, puis effacement (title a AllowClear = true)
.\EquipeLaurence.AdSync.exe --attribute title --value "Chef de division" --user AAlwan
.\EquipeLaurence.AdSync.exe --attribute title --value "" --user AAlwan

Si le service tourne et que la table source contient une autre valeur, le prochain cycle la réécrit. Pour un test durable, arrêter le service ou choisir un utilisateur/attribut absent de la synchronisation.

Normalisation du code unique (AdSync:CodeNormalization)¶

Le code unique est normalisé de la même façon côté table, AllowedUsers, rapprochement et recherche AD (minuscules, accents retirés, espaces retirés).

AdSync:CodeNormalization Effet sur les traits d'union et apostrophes
Keep (défaut) Conservés : ADemers-Forgues est cherché sous ademers-forgues@<suffixe>.
Remove Retirés : ADemers-Forgues est cherché sous ademersforgues@<suffixe>.

Le contrôle de cohérence d'identité (IdentityCrossCheck) compare le code au nom de famille normalisé de la même façon : avec Keep, un code jsaintpierre pour le nom Saint-Pierre devient une incohérence. Si des comptes AD ont un UPN sans trait d'union alors que le code en a un, définir AdSync:CodeNormalization = Remove dans la configuration de l'environnement, puis relancer une simulation et comparer le nombre d'utilisateurs « introuvables » ou « incohérents ».

Déploiement progressif¶

  1. Simulation : AdSync:ApplyEnabled = false (défaut). Chaque cycle calcule les changements et les journalise sans rien écrire. Vérifier les rapports.
  2. Pilote : renseigner AdSync:AllowedUsers (liste restreinte) puis ApplyEnabled = true.
  3. Généralisation : AdSync:AllowAllUsers = true après validation du pilote.

Disjoncteurs¶

  • MaxUsersPerRun (défaut : 1, à relever après le pilote) : nombre maximal d'utilisateurs avec au moins un écart (une écriture potentielle) traités par cycle. Tous les utilisateurs sélectionnés sont comparés à Active Directory ; ceux qui sont déjà à jour ou rejetés ne comptent pas et restent dans le rapport. Au-delà de la limite, les utilisateurs avec écarts sont reportés : rien n'est écrit pour eux, ils n'apparaissent ni dans le tableau ni dans le rapport du cycle, et le journal en donne le nombre (N users with differences deferred to a later run (limited by AdSync:MaxUsersPerRun = M).). L'ordre est celui des codes (ou celui de AllowedUsers) : chaque cycle avance donc vers les suivants.
  • MaxWritesPerRun (défaut : 1) : nombre maximal d'attributs écrits par cycle ; les écarts au-delà ne sont pas écrits (LimitReached) et le seront à un cycle suivant.
  • MaxClearsPerRun (défaut : 1) : un cycle qui viderait plus d'attributs est refusé en entier.
  • MaxDiffPercent / MaxDiffMinPopulation : refus du cycle si les utilisateurs avec écarts retenus pour le cycle (au plus MaxUsersPerRun) dépassent MaxDiffPercent % des lignes actives de la table (évalué à partir de MaxDiffMinPopulation lignes).
  • --backup exporte exactement ce que le prochain cycle écrirait : les utilisateurs reportés n'y figurent pas.
  • Une valeur vide dans la table ne vide un attribut que si AllowClear est vrai pour cet attribut.
  • streetAddress (colonne Address, remplie depuis BD_AdressesBureaux.xlsx selon le bureau) a AllowClear: false : un bureau sans adresse connue (ex. Pas assigné) conserve l'adresse en place dans l'AD (rejet SourceEmpty, rien n'est écrit). Lors d'une mise à jour du service, reporter cette valeur dans l'appsettings.json en place.

Attributs étendus (dates de naissance et d'embauche)¶

Les deux dates sont écrites dans des attributs d'extension natifs d'Active Directory, déclarés dans AdSync:AllowedAttributes (appsettings.json) :

Champ Nethris Colonne de la table Attribut AD AllowClear
Date d'embauche HireDate msDS-cloudExtensionAttribute1 false
Date de naissance BirthDate msDS-cloudExtensionAttribute2 true 
{ "Name": "msDS-cloudExtensionAttribute1", "Format": "IsoDate", "TableColumn": "HireDate", "MinAgeYears": 0, "AllowClear": false, "Sensitive": false },
{ "Name": "msDS-cloudExtensionAttribute2", "Format": "IsoDate", "TableColumn": "BirthDate", "AllowClear": true, "Sensitive": false }
  • Format IsoDate : seule une date yyyy-MM-dd passée est acceptée ; une valeur illisible est rejetée (InvalidValue) sans rien écrire. La date de naissance doit en plus correspondre à un âge de 14 à 100 ans (défaut).
  • BirthDate n'est renseignée dans la table que si l'employé publie sa date d'anniversaire. Quand la colonne est vide (consentement retiré), l'attribut AD est effacé.
  • Une HireDate vide n'efface jamais l'attribut AD : l'écart est rejeté (SourceEmpty) et la valeur existante est conservée.
  • Les deux valeurs sont affichées en clair dans la console interactive (Sensitive: false).
  • Le gMSA du service doit avoir le droit d'écriture sur ces deux attributs, sur les OU des employés seulement.

Adresses des bureaux (OfficeAddressLookup)¶

L'attribut streetAddress est alimenté par la dérivation OfficeAddressLookup à partir du bureau de l'employé :

{
  "Name": "streetAddress",
  "Format": "Text",
  "MaxLength": 1024,
  "TableColumn": "LocationName",
  "Derivation": "OfficeAddressLookup",
  "AllowClear": true,
  "Sensitive": false
}

(L'ancienne configuration TableColumn: "Address" sans dérivation reste valide.) Le service joint LocationName (nom du bureau, normalisé : minuscules, sans accents, sans espaces ni ponctuation) à la table OfficeAddress, alimentée par la synchronisation Nethris → SharePoint (voir le guide de synchronisation), puis écrit l'adresse complète, en une seule chaîne, dans streetAddress.

  • Option AzureTable:OfficeAddressTableName (défaut OfficeAddress) : même compte de stockage et même authentification que AzureTable:TableName ; accès en lecture seule, la table n'est jamais créée par le service (elle l'est à la demande par l'ingestion côté Functions lors de la 1ʳᵉ exécution ; avant cela, streetAddress est ignoré avec un avertissement).
  • Le compte du service a besoin du rôle Storage Table Data Reader aussi sur la table OfficeAddress (scripts\new-adsync-entra-app.ps1, paramètre -OfficeAddressTableName).
Situation Résultat
Bureau renseigné mais absent de la table OfficeAddress streetAddress vidé (AllowClear, borné par MaxClearsPerRun et MaxDiffPercent) et avertissement nommant le bureau
LocationName vide Employé rejeté (OfficeNotSpecified) ; aucun vidage
Table OfficeAddress vide, illisible (403, table absente) ou en erreur de schéma streetAddress n'est pas touché, avertissement ; les autres attributs se synchronisent normalement

Dépannage : une faute de frappe dans la colonne « Description » de BaseTI vide l'adresse de l'employé concerné (corriger BaseTI ou le classeur d'adresses) ; si aucune adresse n'est appliquée, chercher l'avertissement de table vide ou le 403 AuthorizationPermissionMismatch sur OfficeAddress et contrôler l'ingestion côté Functions (EventId 4101 / 4102).

Supérieur immédiat (ManagerLookup)¶

L'attribut AD manager est alimenté par la dérivation ManagerLookup à partir de la colonne Nethris « Supérieur immédiat », stockée dans la table BaseTi sous DirectManagerCode (matricule du supérieur) :

{
  "Name": "manager",
  "Format": "Text",
  "MaxLength": 1024,
  "TableColumn": "DirectManagerCode",
  "Derivation": "ManagerLookup",
  "AllowClear": false,
  "Sensitive": false
}

Chaîne de résolution : DirectManagerCode de l'employé → ligne active de la même table dont le RowKey (matricule) est ce code → UniqueCode de cette ligne → compte AD résolu comme pour tout employé (même rapprochement) → valeur désirée = DN de ce compte, tel que retourné par l'annuaire. Un changement de supérieur dans Nethris est détecté par la comparaison habituelle valeur désirée / valeur actuelle (sauvegarde et restauration inchangées). La table n'est lue qu'une fois et chaque supérieur n'est résolu qu'une fois par exécution.

manager n'est jamais vidé : toute impossibilité de résolution rejette l'attribut (avertissement au journal), la valeur AD existante est conservée. En simulation locale, manager n'est pas pré-rempli à l'initialisation de l'annuaire local (les DN ne sont pas connus) : la 1ʳᵉ exécution le planifie comme un écart.

Situation Raison du rejet
DirectManagerCode vide ManagerNotSpecified
Matricule absent des lignes actives (inexistant ou supérieur inactif) ManagerSourceNotFound
Matricule présent sur plusieurs lignes actives AmbiguousManagerSource
Ligne du supérieur sans UniqueCode ManagerCodeMissing
Compte AD du supérieur introuvable / ambigu / identité non concordante ManagerNotFound / AmbiguousManager / ManagerIdentityMismatch
Le supérieur est l'employé lui-même ManagerIsSelf

Le compte du service doit avoir le droit d'écriture sur l'attribut manager (OU des employés seulement).

Variables d'environnement¶

Les clés se surchargent avec le préfixe ADSYNC_ et __ comme séparateur (ex. ADSYNC_AdSync__ApplyEnabled=true).

ADSYNC_AdSync__AllowPrivilegedIdentity (défaut false) : à laisser à false. Ne le passer à true que par dérogation justifiée, pour qu'un compte privilégié puisse écrire (voir « Identité d'exécution (G15) »).

AdSync:LocalDirectory:Path (simulation avec un annuaire local en JSON, pour le développement sans contrôleur de domaine) doit rester vide sur le serveur : s'il est défini, Active Directory n'est jamais contacté. Lancé comme service Windows, le programme refuse alors de démarrer (code 2).
