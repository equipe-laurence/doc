Proposition — Optimisation des pipelines CI/CD¶

1. Diagnostic — État actuel¶

1.1 Inventaire des workflows¶

Le projet comporte 18 fichiers GitHub Actions. Les 7 workflows principaux (CI/CD applicatif + infra) sont les suivants :

# Fichier Nom Déclencheurs Appelle
1 ci.yml CI — Build & Test PR→develop/main, push→develop function-build.yml
2 deploy.yml Deploy — Application push→develop/main, PR→main function-build.yml + function-deploy.yml
3 function-build.yml Reusable Function Build (réutilisable) —
4 function-deploy.yml Reusable Function Deploy (réutilisable) —
5 infra-deploy.yml Reusable Infrastructure Deploy (réutilisable) —
6 provisioning.yml Provisioning — Infrastructure push→develop/main, PR→main (infra/**) infra-deploy.yml
7 integration-tests.yml Integration Tests schedule (5h UTC), dispatch —

Les 11 workflows Squad (opérationnels) :

# Fichier Chevauchement avec CI/CD ?
8 squad-ci.yml OUI — appelle function-build.yml sur PR→main et push→dev
9 squad-release.yml Non
10 squad-promote.yml Non
11-18 heartbeat, triage, docs, insider-release, labels, etc. Non

1.2 Cartographie des déclencheurs — qui lance quoi et quand¶

┌─────────────────────────┬───────────┬───────────┬───────────┬────────────┐
│ Événement               │ ci.yml    │ deploy.yml│ squad-ci  │ Builds     │
├─────────────────────────┼───────────┼───────────┼───────────┼────────────┤
│ PR → develop            │ ✅ build  │           │ ✅ build │ 2 builds   │
│ PR → main               │ ✅ build  │ ✅ build │ ✅ build  │ 3 builds!  │
│ Push → develop          │ ✅ build  │ ✅ build │           │ 2 builds   │
│ Push → main             │           │ ✅ build  │           │ 1 build ✓  │
│ Schedule (5h UTC)       │           │           │           │ integ. 1   │
└─────────────────────────┴───────────┴───────────┴───────────┴────────────┘

Constat clé : sur 4 événements courants, 3 déclenchent des builds en double ou en triple.

2. Problèmes identifiés¶

🔴 P1 — Double/triple build systématique (gaspillage de minutes)¶

Évidence : Un push sur develop déclenche simultanément ci.yml ET deploy.yml. Les deux appellent function-build.yml — même code, même config, même résultat. Deux workflows complets (restore, build, test, publish, zip, upload) pour un seul commit.

Sur une PR vers main, c'est triple : ci.yml + deploy.yml + squad-ci.yml.

Impact estimé : Chaque build complète prend ~3-5 minutes. Sur un push develop, on gaspille ~4 minutes. Sur une PR main, ~8 minutes. Multipliés par la fréquence des commits, cela représente un gaspillage significatif de minutes GitHub Actions.

🔴 P2 — deploy.yml déclenché sur PR→main sans rien déployer¶

deploy.yml a un trigger pull_request → main. Les jobs de déploiement ont des conditions if qui ne passent que sur push. Résultat : le workflow fait un build complet puis... skip tous les déploiements. C'est un build inutile qui double celui de ci.yml.

🟡 P3 — squad-ci.yml chevauche ci.yml¶

squad-ci.yml déclenche un build sur les branches dev, preview, main, insider. Le trigger PR → main chevauche directement ci.yml. La seule valeur ajoutée est le commentaire PR, qui pourrait être intégré à ci.yml.

🟡 P4 — fetch-depth: 0 dans function-build.yml¶

Le checkout fait fetch-depth: 0 (clone complet de l'historique Git). Aucune étape du build (restore, build, test, publish, package) n'a besoin de l'historique Git. Seul squad-release.yml a besoin du full history, et il fait son propre checkout.

Impact : Sur un repo avec un historique conséquent, le checkout peut prendre 10-30 secondes de plus inutilement, pour chaque build.

🟡 P5 — integration-tests.yml reconstruit tout depuis zéro¶

Le workflow nightly fait dotnet restore + dotnet build de la solution complète (EquipeLaurence.sln) uniquement pour exécuter les tests d'intégration. Il ne réutilise aucun artifact.

Nuance : C'est un run nightly indépendant — la réutilisation d'artifacts cross-workflow est limitée (expiration, workflow_run complexe). L'optimisation possible est de ne builder que le projet de tests d'intégration plutôt que la solution complète.

🟢 P6 — provisioning.yml séquentiel dev→prod¶

Les déploiements infra dev et prod sont séquentiels (needs: [deploy-dev-infra]). Pour un push sur main, seul prod s'exécute (dev est skip). Le séquentiel n'a d'impact que sur les dispatches manuels ciblant all (non implémenté actuellement).

Verdict : Impact faible. Le séquentiel est une protection légitime (Décision 13).

🟡 P7 — Anomalie dans provisioning.yml : push develop déploie aussi en prod¶

Le job deploy-prod-infra a une condition qui, sur un push vers develop, évalue à TRUE (car event_name != 'workflow_dispatch'). Un push infra sur develop tenterait donc de déployer l'infra en prod. Seule la protection d'environnement GitHub (approval gate) empêcherait l'exécution. Ce n'est pas idéal.

3. Approche proposée¶

3.1 Éliminer les double builds — Séparer les responsabilités par événement¶

✅ Appliqué — ci.yml ne déclenche plus que sur PR, deploy.yml ne déclenche plus que sur push.

Principe : chaque événement Git ne doit déclencher qu'UN SEUL build.

Solution retenue : ci.yml = PR only, deploy.yml = push only¶

# ci.yml — AVANT                          # ci.yml — APRÈS
on:                                        on:
  pull_request:                              pull_request:
    branches: [develop, main]                  branches: [develop, main]
  push:                        ← RETIRER      paths: [src/**, tests/**, ...]
    branches: [develop]        ← RETIRER     workflow_dispatch:
  workflow_dispatch:

# deploy.yml — AVANT                      # deploy.yml — APRÈS
on:                                        on:
  push:                                      push:
    branches: [develop, main]                  branches: [develop, main]
  pull_request:                ← RETIRER       paths: [src/**, tests/**, ...]
    branches: [main]           ← RETIRER     workflow_dispatch: ...
  workflow_dispatch: ...

Résultat :

Événement Avant Après
PR → develop 2 builds (ci + squad-ci) 1 build (ci)
PR → main 3 builds (ci + deploy + squad-ci) 1 build (ci)
Push → develop 2 builds (ci + deploy) 1 build (deploy → build + deploy-dev)
Push → main 1 build (deploy) 1 build (deploy → build + deploy-prod)

Réduction : de 8 builds cumulés à 4 pour le même ensemble d'événements — 50% de réduction.

Impact sur les branch protection rules¶

Les branches develop et main exigent le status check "CI — Build & Test". Ce check est produit par ci.yml qui ne se déclenche que sur les PRs. C'est exactement le bon comportement — les status checks sont évalués sur les PRs, pas sur les pushes directs (qui sont bloqués par l'exigence de PR de toute façon).

⚠️ Vérification nécessaire : Confirmer le nom exact du status check dans les branch protection rules GitHub. Il pourrait être CI — Build & Test (nom du workflow) ou Build and test / Build, Test, and Package (format job/reusable-job). Selon le format, aucun changement aux rules n'est nécessaire.

3.2 Résoudre le chevauchement squad-ci.yml¶

✅ Appliqué — squad-ci.yml a été refondu : il cible maintenant uniquement la branche preview et exécute des tests Node.js. Le chevauchement avec ci.yml est éliminé.

Option A (recommandée) : Retirer main de la liste des branches de squad-ci.yml :

# squad-ci.yml
on:
  pull_request:
    branches: [dev, preview, insider] # 'main' retiré
  push:
    branches: [dev, insider]

Le commentaire PR sur les PRs vers main serait couvert en ajoutant la fonctionnalité de commentaire directement dans ci.yml. Cela évite d'avoir deux builds identiques sur les PRs main.

Option B (alternative) : Laisser squad-ci.yml tel quel si les branches dev/insider/preview sont considérées comme un domaine Squad distinct. Dans ce cas, seul le retrait de main est nécessaire.

3.3 Optimiser fetch-depth dans function-build.yml¶

✅ Appliqué — fetch-depth: 1 est en place.

Changer fetch-depth: 0 en fetch-depth: 1 (shallow clone) :

- name: Checkout repository
  uses: actions/checkout@v4
  with:
    fetch-depth: 1 # Était 0 — aucune étape n'a besoin de l'historique

Gain estimé : 5-30 secondes par build selon la taille du repo. Aucun risque — le build, les tests et le packaging n'utilisent jamais Git.

3.4 Optimiser integration-tests.yml¶

✅ Appliqué — le build cible maintenant tests/EquipeLaurence.IntegrationTests plutôt que la solution complète.

Remplacer le build de la solution complète par le build ciblé du projet de tests :

# AVANT
- run: dotnet restore EquipeLaurence.sln
- run: dotnet build EquipeLaurence.sln --configuration Release --no-restore

# APRÈS
- run: dotnet restore tests/EquipeLaurence.IntegrationTests
- run: dotnet build tests/EquipeLaurence.IntegrationTests --configuration Release --no-restore

Gain : Ne compile que le projet de tests et ses dépendances transitives (Core, Infrastructure). Évite de compiler Functions et les autres projets de tests inutilement.

3.5 Corriger l'anomalie provisioning.yml (P7)¶

✅ Appliqué — le trigger push a été retiré entièrement de provisioning.yml. Les déploiements infra passent exclusivement par workflow_dispatch.

Ajouter une condition de branche explicite au job deploy-prod-infra :

deploy-prod-infra:
  needs: [deploy-dev-infra]
  if: |
    always() &&
    (needs.deploy-dev-infra.result == 'success' || needs.deploy-dev-infra.result == 'skipped') &&
    (
      (github.event_name == 'push' && github.ref == 'refs/heads/main')
      || (github.event_name == 'workflow_dispatch' && inputs.target-environment == 'prod')
    )

Cela garantit que seul un push vers main (ou un dispatch explicite) déclenche le déploiement infra en prod.

3.6 Parallélisation — Évaluation¶

Candidat Parallélisable ? Recommandation
Build + infra deploy Oui, dans deploy.yml via workflow_dispatch avec deploy-infrastructure: true Déjà parallèle — les jobs infra n'ont pas de needs: build sauf pour le deploy app
Tests unitaires vs BDD vs function tests Techniquement oui (matrix ou jobs séparés) Non recommandé pour l'instant — le test suite est petit (~quelques secondes). Le overhead de parallélisation (3 runners, 3 restores, 3 builds) serait supérieur au gain
Dev vs prod infra Possible mais non recommandé Garder séquentiel — protection cascade (Décision 13)

3.7 Build once, deploy everywhere — Déjà en place¶

L'architecture actuelle utilise déjà ce pattern via function-build.yml (produit un artifact) + function-deploy.yml (consomme l'artifact). Le problème n'est pas l'absence de réutilisation d'artifacts mais le déclenchement multiple du même build. La solution 3.1 résout ce problème.

┌─────────────────────────┬───────────┬────────────┬───────────┬────────────┐
│ Événement               │ ci.yml    │ deploy.yml │ squad-ci  │ Builds     │
├─────────────────────────┼───────────┼────────────┼───────────┼────────────┤
│ PR → develop            │ ✅ build  │            │           │ 1 build ✓  │
│ PR → main               │ ✅ build  │            │           │ 1 build ✓  │
│ Push → develop          │           │ ✅ build   │           │ 1 build ✓  │
│                         │           │  + deploy  │           │            │
│ Push → main             │           │ ✅ build   │           │ 1 build ✓  │
│                         │           │  + deploy  │           │            │
│ PR → dev/preview/insider│           │            │ ✅ build  │ 1 build ✓  │

Chaque événement = exactement 1 build. Zéro duplication.

5. Risques et considérations¶

# Risque Probabilité Mitigation
R1 Le status check requis CI — Build & Test pourrait ne plus matcher si le nom est basé sur le workflow name Moyenne Vérifier le nom exact dans les branch protection settings avant de modifier ci.yml. Ajuster si nécessaire
R2 Retirer le push trigger de ci.yml signifie que les pushes directs sur develop (si permis) ne sont plus validés par CI Faible Branch protection exige une PR → les pushes directs sont déjà bloqués
R3 squad-ci.yml sur les branches dev/insider pourrait chevaucher ci.yml si ces branches sont aussi protégées Faible Actuellement ci.yml ne cible que develop et main — pas de chevauchement
R4 Réduire fetch-depth à 1 pourrait casser un step futur qui aurait besoin de l'historique Très faible Aucun step actuel ne l'utilise. Si besoin futur, remettre fetch-depth: 0 dans le workflow appelant
R5 Le fix de provisioning.yml (P7) changerait le comportement actuel — les pushs develop ne déploieraient plus en prod Intentionnel C'est le comportement souhaité. Un push infra sur develop ne devrait pas toucher prod

6. Estimation d'effort¶

Modification Effort Complexité
3.1 — Séparer triggers ci.yml / deploy.yml 15 min Faible — retirer 4-6 lignes YAML
3.2 — Retirer main de squad-ci.yml 5 min Trivial
3.3 — fetch-depth: 1 dans function-build.yml 2 min Trivial
3.4 — Build ciblé dans integration-tests.yml 5 min Faible
3.5 — Fix condition provisioning.yml 10 min Faible — déjà un pattern établi dans deploy.yml
Vérification branch protection rules 10 min Faible — lecture seule dans les settings GitHub
Test end-to-end (PR + push sur develop) 20 min Faible — observation des runs
Total ~1h

Tout peut être livré dans un seul commit sur une branche feature, testé via une PR vers develop.

7. Questions pour Eric¶

  1. Status check name : Peux-tu vérifier dans les settings GitHub (Repo → Settings → Branches → Branch protection rules → develop/main) quel est le nom exact du status check requis ? C'est soit CI — Build & Test soit Build and test / Build, Test, and Package. Cela détermine si on doit ajuster les rules après le changement.

  2. squad-ci.yml sur main : Est-ce que le commentaire PR automatique de squad-ci.yml est souhaité sur les PRs vers main ? Si oui, je peux intégrer cette fonctionnalité dans ci.yml plutôt que de garder un build séparé.

  3. provisioning.yml anomalie prod : Confirmes-tu que les pushes infra sur develop ne devraient PAS déployer en prod ? (Le fix proposé en 3.5 empêcherait ce comportement.)

  4. Branches dev/insider : Les branches dev et insider sont-elles encore utilisées activement ? squad-ci.yml les cible mais ci.yml ne couvre que develop et main. Si elles ne sont plus utilisées, on pourrait simplifier squad-ci.yml.
