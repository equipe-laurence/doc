Plan d'implémentation — Synchro Nethris → AD → Entra ID¶

Conception : docs\superpowers\specs\2026-10-19-ad-custom-attributes-signature-design.md (approuvée). Base de code : POC EquipeLaurence.AdSync / EquipeLaurence.AdSync.Poc sur la branche squad/159-adsync-poc-core (.NET 10, LDAP signé/chiffré, simulation par défaut, sauvegarde DPAPI, listes autorisée et noire).

Règle générale : tout reste en simulation (ApplyEnabled=false) jusqu'à la phase 6. Chaque phase se termine par des tests verts.

Phase 0 — Prérequis hors code (en parallèle, bloquants pour les phases 4 à 6)¶

  1. Demander à l'administrateur système de créer les deux attributs de schéma (date de naissance, date d'embauche) : lDAPDisplayName, OID, syntaxe, mono-valué, classe auxiliaire rattachée à user. Attendre la réplication.
  2. Décider l'hôte (joint au domaine) et créer le gMSA. Déléguer l'écriture sur givenName, sn, displayName, title, telephoneNumber, mobile, physicalDeliveryOfficeName, streetAddress et les deux attributs étendus (msDS-cloudExtensionAttribute1 pour la date d'embauche, msDS-cloudExtensionAttribute2 pour la date de naissance), sur les OU des employés seulement.
  3. Donner au gMSA un accès en lecture seule à la Table Azure (rôle RBAC « Storage Table Data Reader »).
  4. Confirmer les hypothèses : Bureau → physicalDeliveryOfficeName, Adresse → streetAddress, format de displayName, fréquence d'exécution, OU ciblées.
  5. Identifier l'outil de signature et confirmer qu'il lit les attributs standards (Entra ID ou AD).

Phase 1 — Étendre l'ingestion Nethris → Table Azure¶

  1. Ajouter à BaseTiRecord et au dépôt de la Table : Tél. travail, Adresse, indicateur « partager le cellulaire », date de naissance, date d'embauche, DisplayName si utile.
  2. Mettre à jour l'import (fichier de référence References\BDNethris_BaseTI.xlsx, BaseTiIngestionService) et ses tests (BaseTiIngestionServiceTests, BaseTiReferenceWorkbookTests, BaseTiArchitectureContractTests).
  3. Si les colonnes n'existent pas encore dans Nethris, tout de même prévoir les colonnes optionnelles dans la Table.

Phase 2 — Intégrer le POC et définir le modèle de synchro¶

  1. Rapatrier la branche du POC (rebase ou fusion sur main) via une branche squad/{issue}-adsync-sync.
  2. Définir dans la configuration la table de correspondance : champ Table → attribut AD, avec format, longueur max, AllowTableSync, AllowClear=true, et indicateur de donnée sensible pour les dates.
  3. Ajouter à la liste autorisée les attributs de la phase 0. Vérifier que displayName, physicalDeliveryOfficeName et streetAddress ne sont pas dans la liste noire.
  4. Les noms des attributs étendus sont lus de la configuration (aucun nom codé en dur).

Phase 3 — Exécuteur de réconciliation (cœur du service)¶

Tests d'abord pour chaque règle.

  1. Lire tous les enregistrements de la Table (lecture seule).
  2. Filtrer : ignorer les employés au statut « Terminé » et les comptes AD désactivés.
  3. Trouver l'utilisateur par userPrincipalName = <Code unique>@<suffixe>. Sans correspondance : journaliser et ajouter au rapport d'exceptions (taux de correspondance).
  4. Calculer les valeurs cibles : displayName = Prénom + Nom, mobile seulement si « partager » = oui, sinon valeur vide.
  5. Comparer à l'AD : valeur différente → remplacer, valeur cible vide → effacer, identique → rien.
  6. Valider le format avant écriture (dates ISO ou heure généralisée selon la syntaxe lue dans le schéma, longueurs, téléphone).
  7. Produire un plan de changements par utilisateur et attribut (le rapport de simulation).

Phase 4 — Validation du schéma et garde-fous¶

  1. Au démarrage, lire le schéma (schemaNamingContext, attributeSchema) et refuser tout attribut absent ou de syntaxe incompatible.
  2. Frein de sécurité 🔸 : seuils configurables de nombre de changements et d'effacements ; dépassement = exécution refusée (code de sortie 4).
  3. Conserver les gardes du POC : refus d'une identité privilégiée ou SYSTEM, liaison sécurisée obligatoire avec ApplyEnabled=true.
  4. Sauvegarde protégée avant chaque écriture, avec restauration. Journaux sans valeur de date de naissance en clair.

Phase 5 — Hébergement en service Windows¶

  1. Héberger l'exécuteur comme service Windows (Microsoft.Extensions.Hosting.WindowsServices) avec une planification configurable.
  2. Journalisation (fichier ou journal d'événements) et codes de sortie du POC (0 à 4).
  3. Package et script d'installation : service sous le gMSA, configuration par appsettings.json et variables ADSYNC_, sans secret.

Phase 6 — Déploiement progressif (aucun AD de test)¶

  1. Simulation en production : exécuter en lecture seule, relire le rapport complet et le rapport d'exceptions avec les RH.
  2. Pilote : activer l'écriture pour quelques comptes nommés. Vérifier dans l'AD, puis après un cycle Entra Connect (~30 min) dans Entra ID (Graph : attributs standards et extension_<appId>_<nom>).
  3. Entra Connect : « Refresh Directory Schema », puis choisir les deux attributs dans Directory extensions.
  4. Vérifier l'outil de signature sur les comptes pilotes.
  5. Étendre à toutes les OU. Planifier l'exécution récurrente.
  6. Documenter l'exploitation : lecture des rapports, restauration, ajout d'un attribut.

Critères de fin¶

  • Rapport de simulation relu et approuvé avant la première écriture.
  • Pilote validé de bout en bout (AD, Entra ID, signature Outlook).
  • Aucune écriture dans mail, userPrincipalName, sAMAccountName, mots de passe ou groupes.
  • Restauration testée sur un compte pilote.

Risques à surveiller¶

  • Colonnes manquantes dans Nethris (phase 1) : bloque les dates, le téléphone de travail et l'adresse.
  • Aucun AD de test : la simulation et le pilote sont la seule protection.
  • Effacement des valeurs vides : peut vider des signatures si Nethris est incomplet (frein de sécurité).
  • Date de naissance : donnée sensible dans l'AD, Entra ID, sauvegardes et journaux.
