Attributs AD personnalisés, synchro Entra ID et signatures Outlook — Conception¶

Statut : révisé après les réponses de l'utilisateur, en attente d'approbation. Aucune construction avant approbation.

Objectif¶

Faire de Nethris la source de vérité des informations employé dans l'AD local, les propager vers Entra ID via Entra Connect, et les rendre disponibles à l'outil de signature Outlook. Comprendre la mécanique de bout en bout, car l'équipe écrira le service Windows qui met à jour l'AD.

Chaîne de données¶

  1. Nethris → Azure Function → Table Azure (BaseTI). Existe déjà.
  2. Table Azure → service Windows (à construire) → AD local (LDAP).
  3. AD local → Entra Connect (déjà installé, cycle delta ~30 min) → Entra ID.
  4. Entra ID → outil de signature → Outlook.

Champs¶

Colonnes Nethris à synchroniser : Code unique, Prénom, Nom, Tél. cellulaire (seulement si la colonne « partager… » vaut « oui »), Tél. travail, Bureau (champ « Description » du fichier References\BDNethris_BaseTI.xlsx), Titre pour signature (SignatureTitle), Adresse (une seule ligne).

Champ Nethris Attribut AD Synchro vers Entra ID
Code unique clé de correspondance (jamais écrit) —
Prénom givenName native
Nom sn native
Prénom + Nom displayName (suit givenName et sn) native
Titre pour signature (colonne SignatureTitle, en-tête « Titre pour signature ») title native
Tél. travail telephoneNumber native
Tél. cellulaire (si partage = oui), valeur brute (colonne MobilePhoneRaw, non normalisée) mobile native
Bureau physicalDeliveryOfficeName 🔸 native
Adresse (une ligne) streetAddress 🔸, sans découpage native
Date de naissance (colonne BirthDate) msDS-cloudExtensionAttribute2 (effacé si non publiée) à vérifier
Date d'embauche (colonne HireDate) msDS-cloudExtensionAttribute1 à vérifier

Hors synchro : mail reste en lecture seule (jamais écrit par le service).

Les deux dates ne vont pas dans la signature : la signature n'utilise que des attributs standards.

🔸 Hypothèses à confirmer : Bureau → physicalDeliveryOfficeName, et l'adresse en une ligne → streetAddress seul (ville, province et code postal ne sont pas renseignés séparément).

⚠️ Écart à combler : la Table BaseTI actuelle (BaseTiRecord, fichier de référence BDNethris_BaseTI.xlsx) ne contient ni date de naissance, ni date d'embauche, ni téléphone de travail, ni adresse, ni colonne « partager… ». L'Azure Function (étape 1) doit être étendue, ou ces colonnes sont déjà prévues dans une version à venir.

Règles décidées¶

  • Nethris est la source de vérité : le service écrase les valeurs de l'AD.
  • Valeur Nethris vide : l'attribut AD est effacé. Cela s'applique aussi à mobile quand « partager… » ≠ « oui », et à la date de naissance quand elle n'est pas publiée. Exception : une date d'embauche vide n'efface pas l'attribut AD (la valeur existante est conservée).
  • Employés partis (statut « Terminé ») ou comptes AD désactivés : ignorés.
  • Employé sans compte AD correspondant : ignoré et journalisé, avec un rapport d'exceptions (taux de correspondance Code unique ↔ UPN).
  • Clé de correspondance : Code unique Nethris = « User logon name » AD. Recherche sur userPrincipalName = <Code unique>@<suffixe>, suffixe unique et configurable.
  • Les dates sont écrites dans les attributs d'extension natifs msDS-cloudExtensionAttribute1 (date d'embauche) et msDS-cloudExtensionAttribute2 (date de naissance) : aucune extension du schéma AD n'est requise (décision du 2026-10-27, qui remplace la décision initiale d'étendre le schéma).
  • Le service s'appuie sur le POC existant (EquipeLaurence.AdSync, branche squad/159-adsync-poc-core) : liste d'attributs autorisés, liste noire, simulation par défaut, sauvegarde et restauration, refus des identités privilégiées.

Sécurité du déploiement (aucun AD de test)¶

Comme Nethris écrase l'AD, que les valeurs vides effacent, et qu'aucun environnement de test n'existe, la simulation devient une exigence centrale :

  1. Simulation (dry-run) obligatoire en premier : rapport complet des changements prévus par utilisateur et attribut, sans écriture. C'est le mode par défaut du POC.
  2. Pilote : activer l'écriture sur quelques comptes nommés avant toute unité d'organisation entière.
  3. Frein de sécurité 🔸 : refuser une exécution dont le nombre de changements ou d'effacements dépasse un seuil configurable.
  4. Sauvegarde avant écriture et restauration, déjà prévues dans le POC (protégées, car elles contiennent la date de naissance).

Comment référencer un attribut de schéma étendu¶

  • En LDAP, l'attribut est désigné par son lDAPDisplayName, comme n'importe quel attribut standard.
  • L'administrateur doit fournir pour chaque attribut : lDAPDisplayName, syntaxe (chaîne Unicode 2.5.5.12 ou heure généralisée 2.5.5.11), mono-valué, et la classe auxiliaire rattachée à user.
  • La syntaxe détermine le format d'écriture (chaîne ISO yyyy-MM-dd ou yyyyMMddHHmmss.0Z).
  • Le service valide au démarrage l'existence et la syntaxe de l'attribut via le schéma (RootDSE schemaNamingContext, objets attributeSchema), comme list --schema du POC.
  • Le schéma doit être répliqué à tous les contrôleurs de domaine avant la première écriture.
  • Les noms étant à définir, ils sont configurables : la livraison peut se faire par phases (attributs standards d'abord, dates ensuite).

Entra Connect¶

  • Relancer « Refresh Directory Schema », puis choisir les deux attributs dans Directory extensions.
  • Ils apparaissent dans Entra ID sous extension_<appId>_<nom>, lisibles par Microsoft Graph.
  • Ils ne sont pas visibles dans Exchange Online ni Outlook.

Identité, hôte et secrets¶

  • Selon les bonnes pratiques : hôte joint au domaine, gMSA (compte de service géré) avec droits délégués en écriture uniquement sur les attributs listés, dans les unités d'organisation des employés.
  • Accès à la Table Azure en lecture seule via identité managée ou DefaultAzureCredential (déjà utilisé par le POC), sans secret dans la configuration.
  • Le service ne doit jamais s'exécuter avec une identité privilégiée ou SYSTEM (garde existante du POC).

Prérequis et risques¶

  • L'outil de signature est inconnu. Il doit lire les attributs standards depuis Entra ID ou l'AD. Les attributs étendus n'ont pas besoin de lui être visibles.
  • Délai de bout en bout : cycle du service + cycle Entra Connect (~30 min) + rafraîchissement de l'outil de signature.
  • La date de naissance est sensible : accès restreint dans Entra ID, journaux et sauvegardes protégés.
  • Le POC n'a jamais tourné sur un vrai AD. L'exécuteur complet (réconciliation, multi-attributs, multi-utilisateurs) reste à construire.
  • Vérifier que displayName, physicalDeliveryOfficeName et streetAddress ne sont pas dans la liste noire du POC, et les ajouter à la liste autorisée.

Hors périmètre¶

  • Choix et configuration de l'outil de signature.
  • Écriture dans mail, userPrincipalName, sAMAccountName, mots de passe ou groupes.
  • Création de comptes AD.
  • Découpage de l'adresse en ville, province et code postal.

Questions encore ouvertes¶

  1. Les colonnes manquantes (dates, téléphone de travail, adresse, « partager… ») : qui étend l'Azure Function et la Table, et quand ?
  2. lDAPDisplayName, OID et syntaxe des deux attributs de schéma (à définir avec l'administrateur).
  3. Fréquence d'exécution du service et unités d'organisation ciblées.
  4. Confirmation des deux hypothèses 🔸 (Bureau, Adresse) et du format de displayName.
